## Среда и границы проверки

Облачный Linux, Python 3.12.14, SQLite 3.53.1, установленные зависимости проекта,
Playwright Chromium. Пользовательский компьютер не использовался. Базы проверок —
временные, созданные из действующей схемы; настоящая SQLite пользователя не читалась.

HH.ru заменён локальными тестовыми страницами/источниками. Браузерные сценарии
используют настоящий Chromium, локальный Flask и перехват тестовых URL.
DeepSeek заменён сценарными ответами либо настоящим DeepSeekClient с подменённым
HTTP-opener. Последнее проверяет транспорт/бюджет, не обращаясь к провайдеру.
Реальных запросов HH, авторизации в аккаунты и платных генераций не было.

## Найденные дефекты и исправления

### D1. Квота HH ошибочно ограничивала переоценку локальной подборки

`get_results` выбирал ID с LIMIT=max_source_vacancies. При двух готовых карточках,
изменившихся критериях и квоте HH=1 обновлялась только одна оценка; вторая исчезала
из актуальной выдачи, хотя квота предназначена для сбора источника.

Убран этот LIMIT из выборки прикреплённых к задаче ID. Переоценка по-прежнему
ограничена временем и своим LLM-бюджетом, а размер показанной выдачи — results.
Новых квот, очередей и обхода HH это не добавляет.

Регрессия: `test_hh_discovery_quota_does_not_cap_local_result_reassessment`.

### D2. Очистка диагностического файла меняла возрастной фильтр при просмотре деталей

`get_details` брал окно из TaskTrace и при его отсутствии переходил к глобальному
значению. После очистки файла недельное окно могло превратиться в 30 дней и
разрешить лишнюю платную переоценку 15-дневной карточки.

Окно теперь читается из сохранённого `search_tasks.search_queries` независимо от
наличия файла диагностики. Для старых задач без окна остаётся прежний fallback.

Регрессия: `test_detail_refresh_honors_persisted_task_period_after_trace_pruning`.

### D3. Сетевые повторы обходили счётчики вызовов модели

StructuredLLM расходовал один вызов, а DeepSeekClient мог внутри выполнить до трёх
HTTP-попыток. То же расхождение было в лимите диалоговой реплики. При бюджете 1
после сетевого отказа допускался второй запрос.

Добавлен внутренний callback on_retry: перед повторным HTTP-запросом резервируется
ещё один вызов соответствующего бюджета. Исчерпание бюджета блокирует повтор;
SearchService откладывает анализ, но продолжает сохранять HH-исходники, пока
действуют остальные ограничения. Структурная попытка исправления тоже сохраняет
прежний учёт. Запись диагностик не теряется при SearchStop из транспорта.

В метаданных LLM есть transport_attempts; итог основного поиска содержит
specialized_llm_calls. Это попытки специализированных вызовов, включая ошибки и
повторы, не денежный бюджет. Диалоговые вызовы учитываются отдельно. Провайдер
может не вернуть usage при сбое, поэтому точная стоимость из локальных логов
не гарантируется.

Регрессии: `test_transport_retry_must_obey_shared_specialized_budget`,
`test_allowed_transport_retry_is_charged_and_raw_collection_survives_exhaustion`,
`test_retry_success_counts_two_attempts_without_changing_response_contract`,
`test_dialogue_transport_retries_obey_its_own_turn_budget`.

### D4. Некоторые необязательные числовые настройки принимали null

Загрузчик принимал явно записанный null для max_llm_calls, target_count,
max_tokens, ожидания ручного действия/контента и лимитов диагностик. Затем код
использовал их как числа, что могло дать TypeError или некорректный параметр модели.

Отсутствующий необязательный ключ по-прежнему использует значение по умолчанию;
явный null теперь выдаёт понятную ошибку загрузки с именем настройки. null для
vacancy_max_age_days остаётся допустимым осознанным отключением фильтра.
Конфигурационные файлы и их численные значения не менялись.

Регрессия: `test_optional_positive_config_values_reject_explicit_null` (9 вариантов).

### D5. Конфликт региона плана и сохранённой географии скрывался

При criteria.locations=Россия и плане areas=Казахстан сервер молча подставлял
Россию. В ответ на разовую просьбу мог выполняться поиск не в ожидаемом регионе.
Полноценной модели разовой географии в текущем внутреннем плане нет.

Минимальное исправление — обнаружить конфликт и запросить уточнение до HH,
не менять критерии и не выполнять поиск в другом регионе молча. Географические
группы, уже разрешённые прежним механизмом, и старое обозначение удалёнки отдельно
сохраняются. Промпты больше не обещают полную разовую смену сохранённой географии.

Регрессия: `test_conflicting_planner_region_is_not_silently_replaced_by_saved_region`.
Полная разовая география остаётся ограничением: потребовалось бы определить её
применение к локальному фильтру, оценке и кэшу, а не только подставить URL HH.
Такое расширение в этапе 4 не реализовано.

## Что остаётся проверить пользователю

[Пошаговая инструкция Windows](v0.2-local-acceptance.md) содержит отдельную копию
базы, hh-login, запуск с журналом, проверку DeepSeek, сообщения чата и ожидаемые
результаты, диагностику, снимки карточек/критериев и сверку лимитов/токенов.

Не подтверждено облачной проверкой:

- Windows/Python/Chromium в конкретной системе, пользовательский прокси и сертификаты.
- Реальная авторизация HH, актуальная разметка, CAPTCHA и доступность объявлений.
  Например, обработка текущей страницы архива с HTTP 200 зависит от фактически
  доступных признаков сайта и должна проверяться на реальном примере, не выдуманной
  тестовой разметке. Прежний адаптер не перерабатывался.
- Действующий ключ, баланс, доступность модели, качество Tool Calling и понимание
  свободных формулировок. Моки не доказывают исправление всех ответов живой модели.
- Содержимое и история конкретной накопленной SQLite, существующие карточки и
  критерии. На копии нужно проверить повторы, разовые/сохранённые периоды и их ревизии.
- Реальные расходы, скорость и полнота подборки. Цель результатов не гарантирует
  достаточность, а успешные usage не заменяют счёт провайдера.

Унаследованные ограничения: синхронная обработка, отсутствие автопродолжения после
перезапуска, чтение выдачи до 1000 кандидатов, неопределённые даты не отсекаются,
распределение квоты между фразами и критерий достаточности остаются открытыми.
Полная разовая смена сохранённой географии не реализована; теперь конфликт явный.

**Завершение этой части этапа 4 не означает приёмку JobRadar v0.2.** Пользователь
должен выполнить локальные сценарии и принять решение по результатам.
