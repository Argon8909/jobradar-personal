# JobRadar v0.1 — DeepSeek, Dialogue Agent и Tool Dispatcher

## Готово

- DeepSeekClient: HTTP Chat Completions, Tool Calling, JSON mode, конфигурация,
  чтение ключа из окружения или локального .env, таймаут, максимум два безопасных
  повтора генерации на сетевых сбоях, HTTP 429/5xx. HTTP 401/4xx и некорректный
  структурированный ответ не повторяются. Обрезанная генерация не исполняется.
  Исключения не раскрывают ключ, HTTP-body или исходную трассировку.
- ToolRegistry: 11 утверждённых определений, явное подключение обработчиков.
  ToolDispatcher: проверка текущего режима, точных аргументов JSON Schema,
  владельца, редакций и привязки разрешения к конкретному действию.
  Единые ответы success/data и error/code/message/retryable.
- Подключены восемь методов ProfileManager. После смены контекста набор tools
  пересчитывается перед следующим LLM-запросом, а режим повторно проверяется перед
  каждым вызовом, в том числе внутри одного batch ответа модели.
- DialogueAgent: ограниченный цикл Tool Calling, история, выдача результата
  инструмента модели и подтверждённые уведомления об изменениях.
- Orchestrator: соединяет компоненты и сериализует диалог пользователя; не содержит
  SQL, HH-логику или реализацию отдельных инструментов.
- Терминальный запуск: python -m jobradar chat [--session ID]. Flask UI — следующий этап.

## Согласие и семантика

Определение намерения выполняет тот же Dialogue Agent с неизменённым dialogue.md
версии 1.0 в отдельном структурированном запросе без tools. Python проверяет выходную
структуру, аргументы, дословное наличие evidence в текущей реплике и связывает
разрешение с точной командой и аргументами. История/профиль передаются отдельными
сообщениями-данными, системный текст не изменялся. Семантическое решение, является ли
реплика намерением/согласием, остаётся вероятностным решением LLM, как предусмотрено
документацией; Python не заменяет его набором ключевых слов.

Предложение, сформулированное обычным текстом, тоже извлекается структурированным
запросом. Оно не исполняется и хранится только в памяти процесса, с точными
параметрами и снимком контекста/редакций. Ответ «да» разрешает только это действие.
Смена темы, несовпадение снимка или перезапуск аннулируют ожидание. Если извлечение
предложения не удалось, разрешение не выдаётся; остаётся возможность явной команды.
Согласие не является аргументом инструмента и не может быть подставлено LLM в JSON.

Лимиты: 20 Tool Calls на пользовательский запрос; до 24 логических LLM-запросов
на ход, включая структурированные проверки. Максимум два транспортных повтора
считаются отдельно. Значения вынесены в конфигурацию. Изменяющие Python-операции
автоматически не повторяются: при неизвестном исходе коммита это могло бы создать
дубли. Повтор того же tool_call_id с теми же аргументами внутри хода возвращает
сохранённый результат; смена аргументов при том же ID отклоняется.

## Хранение

Логическая схема БД не менялась. Полный протокол assistant/tool сохраняется JSON-конвертом
в существующем messages.content; role, владелец, сессия и context_id — штатные поля.
Новые таблицы подтверждений не вводятся. В следующий ход передаётся разговорный текст
и свежее состояние БД, а исторические tool_calls не воспроизводятся — обрезанная
история или остановка процесса не создают orphan tool messages в запросе к API.
После частично успешного хода подтверждённые операции сохраняются даже при сбое LLM.

## Проверки и границы

67 тестов v0.1 и 9 регрессионных тестов v2.2. Покрыты согласие на предложение
(включая предложение обычным текстом), смена темы/контекста, недопустимые аргументы,
доступ к чужим данным, безопасные повторы клиента, санитарная обработка ошибок,
смена режимов внутри batch, лимиты цикла, повтор ID, история после пересоздания
оркестратора и сохранение результата при отказе последующего LLM-запроса.

Тесты используют подставные ответы DeepSeek и реальные временные SQLite-файлы.
Реальная совместимость модели/качество распознавания намерения требуют проверки
с локальным ключом; ключ не запрашивался и платные сетевые запросы не выполнялись.
Проверки выполнены на Linux/Python 3.12; Windows-инструкция подготовлена.

search_vacancies, get_search_results и get_vacancy_details пока возвращают
SOURCE_UNAVAILABLE. Интерфейс регистрации позволит подключить Search Manager,
не меняя основной цикл. Не реализованы HH, Vacancy Analyzer, Tag Resolver и Flask UI.
Следующий крупный этап — Flask-чат поверх готового оркестратора.
