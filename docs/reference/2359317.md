**Статус:** согласованный состав инструментов Dialogue Agent для v0.1; теперь 11 команд с учётом возврата в общий режим. Перечень и ограничения режимов закреплены. Полные машинно-читаемые входные определения всех инструментов размещены в [Tool Calling — полные JSON Schema 11 команд](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/2490371/Tool+Calling+JSON+Schema+11). В этой странице остаются правила доступа и краткие логические контракты.

## Правило режимов

**Общий режим:** `user_sessions.active_context_id = NULL`. Только `list_profiles`, `create_profile`, `switch_context`. Никакого поиска, оценки вакансий или редактирования существующих профилей. `list_profiles` возвращает также краткие сведения и идентификаторы принадлежащих пользователю поисковых контекстов, чтобы `switch_context` не требовал отдельного инструмента общего режима.

**Режим активного контекста:** `active_context_id` указывает на конкретный `search_contexts` и связанный `user_profiles`. Доступны `list_profiles`, `switch_context`, `update_profile`, `list_contexts`, `create_context`, `update_context`, `search_vacancies`, `get_search_results`, `get_vacancy_details`, `return_to_general`. `create_profile` из активного режима недоступен: для новой профессии сначала вернуться в общий диалог через `return_to_general`.

Перед каждым LLM-запросом Orchestrator определяет режим из БД и передаёт DeepSeek **только доступные в этом режиме определения tools**. Tool Dispatcher независимо повторно проверяет режим, принадлежность объектов и права; это не защита только промптом.

## Первый контекст создаётся автоматически

У каждого `user_profiles` минимум один контекст `search_contexts` в завершённом состоянии. `create_profile` атомарно создаёт профиль и первоначальный контекст (по умолчанию «Основной поиск»), без отдельного Tool Call. При ошибке всей операции откатить обе записи. Создание дополнительных контекстов — отдельная функция `create_context`, доступная только из активного контекста. Не допускать удаления последнего контекста (если функциональность удаления появится позднее). Отдельная команда `create_context` в общем режиме не нужна.

## Общая форма ответа

Единый ответ на уровне Tool Dispatcher: `status` (`success`, `error`, потенциально `running`), `data` для успеха и `error: {code,message,retryable}` для ошибки. Для поисковых задач возвращать `task_id` и явное состояние из `search_tasks.status`, не смешивать статус команды со статусом долгой задачи. На ошибке не отдавать SQL-трассировки, секреты или чужие данные.

Единые базовые ошибки: `VALIDATION_ERROR`, `ACCESS_DENIED`, `ACTIVE_CONTEXT_REQUIRED`, `CONFIRMATION_REQUIRED`, `PROFILE_NOT_FOUND`, `CONTEXT_NOT_FOUND`, `TASK_NOT_FOUND`, `VACANCY_NOT_FOUND`, `REVISION_CONFLICT`, `DB_ERROR`, `SOURCE_UNAVAILABLE`, `LLM_ERROR`, `TASK_FAILED`, `TOOL_NOT_ALLOWED`. Их стабильные значения, retryable, маппинг на пользовательский текст и возможные доп. поля уточнить в полной формальной спецификации.

## Контракт передачи в DeepSeek

LLM получает компактные определения инструмента: `type=function`, `function.name`, `function.description`, `function.parameters` (JSON Schema с обязательными и необязательными полями). Полную документацию, правила хранения БД, детали исключений и внутренние функции в каждый запрос не передавать. В описаниях должно быть достаточно информации о том, *когда* допустим вызов; в коде — проверка всех ограничений. Не считать, что модель всегда возвращает одновременно пользовательский текст и Tool Call.

## Что НЕ является инструментами Dialogue Agent

`save_vacancy`, `save_vacancy_card`, `create_tag`, `create_tag_alias`, `link_vacancy_tag`, `execute_sql` — только внутренние функции предметных Python-сервисов. Vacancy Analyzer получает описание вакансии и минимальные критерии, возвращает структурированные данные (карточка, теги, оценка) без Tool Calling для операций сохранения. Tag Resolver тоже может использовать структурированный LLM-ответ для смыслового сопоставления.

## Нерешённые вопросы перед кодом

Входные JSON Schemas закрыты и опубликованы по ссылке выше. По мере реализации уточняются полный справочник кодов ошибок, подтверждение повторных запусков и исполняемые тесты ответов инструментов. Эти вопросы нельзя считать автоматически решёнными из компактной таблицы.

## Уточнения, согласованные в диалоге

**Новый инструмент **`return_to_general`**:** доступен только при активном контексте. Аргументы: пустой объект `{}`. Успешный результат: `active_context_id: null`. Python устанавливает `user_sessions.active_context_id = NULL`, не удаляет профили, контексты и историю сообщений. Естественные формулировки пользователя («выйти из поиска», «вернуться в общий диалог», «хочу обсудить другую профессию») распознаёт LLM. Возможные ошибки: `ACTIVE_CONTEXT_REQUIRED`, `DB_ERROR`.

**Изменение данных и подтверждения:** явная команда пользователя на обновление профиля/критериев выполняется без повторного подтверждения; когда изменение самостоятельно предлагает LLM, сначала требуется согласие. О результате операции пользователь обязательно получает уведомление с конкретными изменёнными значениями (например, «Обновил критерии поиска: зарплата от 200 000 ₽»). На ошибке нельзя сообщать об успешном обновлении.

**Выбор профиля из общего диалога:** если однозначно найден один подходящий профиль с единственным контекстом, допускается автоматически переключиться, уведомив пользователя. Если профилей/подходящих контекстов несколько — спросить выбор. Если подходящего профиля нет — предложить создать. Не требовать отдельного подтверждения для однозначного переключения, инициированного запросом пользователя.

**Указанные при переходе критерии:** явно названные пользователем условия (например, «от 200 тысяч») применяются к выбранному контексту с уведомлением об изменении. Обновление параметров — отдельная операция уже в активном контексте, с проверкой прав/типа данных. Обсуждение сценариев автоматического запуска поиска не считается завершённым и не должно добавляться здесь как правило.

**Не решено:** подробные исходящие JSON-контракты ответов конкретных инструментов (при необходимости); входные схемы согласованы и опубликованы по ссылке выше.

**Принятое решение по update\_profile и update\_context:** LLM передаёт в параметре `changes` только изменяемые поля, а не весь объект профиля или критериев. Python валидирует изменения и применяет частичное обновление, не затрагивая остальные поля. Передача полного объекта для изменения одного параметра не требуется. Вопрос закрыт; вложенная JSON Schema `changes` опубликована по ссылке выше.

## Утверждено: формат вызовов и обработка ошибок

Для всех 11 инструментов используется единый ответ Python → Dialogue Agent: успех `{"status":"success","data":{...}}`, ошибка `{"status":"error","error":{"code":"...","message":"...","retryable":false}}`. Результат инструмента передаётся модели как tool message; системный промпт определяет реакцию на результат, состояние и история находятся в Python/БД. Пользователю сообщать об успехе только после подтверждения Python.

При неверных параметрах LLM может исправить вызов; при отсутствии объекта или доступа — объясняет пользователю; при временном сбое Python допускает максимум **две автоматические повторные попытки** при условии безопасного повтора (защита от дублей для изменяющих операций). Если проблема сохраняется — сообщить о невыполнении.

**Предел:** не более **20 Tool Calls диалогового агента на один пользовательский запрос**; автоматические повторы из-за ошибок учитываются отдельно. Сбор и анализ вакансий выполняются отдельной задачей и не входят в этот предел; для них нужны собственные ограничения по числу вакансий, LLM-вызовам и времени.

## Утверждено: входные команды и сверка с моделью данных

Три команды общего режима и восемь дополнительных активного режима согласованы. `list_profiles`, `list_contexts`, `return_to_general` принимают пустой объект параметров; `switch_context` — `context_id`; `get_vacancy_details` — `vacancy_id`; `get_search_results` — необязательные `task_id`, `limit`; `search_vacancies` — необязательный `request` только для разового уточнения запроса, не изменения сохранённых критериев; `create_context` — `name` и необязательный `criteria`; `create_profile` — `profession` и необязательный `profile_data`; `update_profile`/`update_context` — `changes` (только изменяемые поля).

Вложенные поля `profile_data`, `criteria` и `changes` должны совпадать с контрактами `user_profiles.profile_data` и `search_contexts.criteria`; `profession` не дублируется во входном `profile_data`, `schema_version` формирует Python. Исполняемые вложенные JSON Schemas доступны по ссылке выше.

**Предварительная настройка выдачи:** для `get_search_results` значение `limit` по умолчанию `20`, максимум `100`. Это конфигурация, не окончательный продуктовый норматив; может измениться после тестов. Полные JSON Schemas параметров составлены и сверены с утверждённой моделью БД (см. ссылку выше).

## Решения, закрытые перед реализацией v0.1

**Автоактивация:** после успешного `create_profile` первый контекст активируется в той же логической операции; после `create_context` новый контекст тоже сразу активен. Оба действия сопровождаются уведомлением пользователя. При смене активного контекста Orchestrator обновляет режим и доступный набор инструментов перед следующими вызовами; не исполняет оставшиеся вызовы прежнего режима без перепроверки полномочий.

**Подтверждения:** явный запрос пользователя достаточен для выполнения без дополнительного вопроса. Предложение LLM требует согласия: ответ «да» относится к последнему предложенному конкретному действию. При смене темы ожидающее согласие устаревает; хранится в состоянии текущего диалога без отдельной таблицы БД. Python проверяет наличие основания для действия и соответствие контексту; результат сообщать только после успеха.

**Однозначное переключение:** если подходящий профиль и контекст единственные, переключить и уведомить; при нескольких подходящих вариантах спросить пользователя. При явно указанных новых критериях изменить только соответствующие поля выбранного контекста после перехода. Не запускать поиск автоматически без пользовательского намерения.
