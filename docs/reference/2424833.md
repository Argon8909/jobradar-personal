**Назначение:** единый источник архитектурных решений для целевого MVP JobRadar. В [v0.1](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/1769474/v0.1) документируются только отличия и временные ограничения, а не копии архитектуры.

## Принятый подход

**Модульный монолит на Python.** Один процесс и одна логическая БД на старте; функциональные компоненты изолированы интерфейсами. Оркестратор координирует, но не содержит реализации сбора, нормализации, хранения, интерфейсов или конкретных инструментов. Новые функции подключаются как модули/обработчики через реестр и согласованные интерфейсы, без изменения основного цикла оркестратора. Полноценная динамическая плагинная платформа и микросервисы не требуются.

## Компоненты

| Компонент | Ответственность | Граница |
| --- | --- | --- |
| UI Adapter | Приём сообщений, показ ответа, состояния и событий задач | Flask в v0.1; другие каналы позже |
| Orchestrator | Цикл обработки сообщений, координация сервисов, маршрутизация инструментов, управление задачами | Без логики конкретного сайта и без произвольного SQL от LLM |
| Dialogue Agent + LLM Client | Намерения пользователя, уточнения, выбор разрешённых Tool Calls, ответы | Не получает сырые объявления как системные инструкции |
| Vacancy Analyzer | Отдельный LLM-контекст: извлечение карточки и тегов, первичная оценка по профилю | Нет инструментов изменения профилей/контекстов; может инициировать строго ограниченное сохранение результата через сервис |
| Tag Resolver | Нормализация и поиск существующих тегов/синонимов; вызов LLM для неоднозначных вариантов | Python-сервис, не обязательно отдельный агент |
| Task/Search Manager | Состояние search\_tasks, алгоритм поиска и обработки вакансий, статусы/ошибки | Не зависит от HTTP-запроса или экрана |
| Source Adapters | Поиск и извлечение данных на отдельных сайтах, проверка доступности | HH через Playwright сначала; Avito вакансии и другие источники потом |
| Context/Profile Manager | Чтение и изменение профилей/контекстов, проверка владельца, активный контекст | Отделён от языковой интерпретации |
| Storage Service | Валидация структур, SQL, транзакции, дедупликация и ограничения | SQLite допустима для v0.1, PostgreSQL позднее |

## Подключение новых функций и источников

Модуль предоставляет публичный контракт (имя/возможности/входы/выходы/ошибки), регистрирует свои обработчики, не изменяя внутренний код оркестратора. Источники имеют согласованные операции вроде поиска, получения полного объявления и проверки статуса; различия HTML/API скрыты внутри адаптера. Единый формат данных для вакансий определяется моделью Database. Подключение Avito как *источника вакансий* допустимо через адаптер; отдельные радары для автомобилей и недвижимости не должны автоматически использовать ту же предметную модель вакансий — это самостоятельные продукты/модули верхнего уровня и отдельное проектное решение.

## Логические потоки

**Диалог:** UI → Orchestrator → Dialogue Agent → разрешённый Tool Dispatcher → предметный сервис → результат инструмента → Dialogue Agent → ответ. Текст «начинаю поиск» и инициирование операции могут относиться к одному логическому ходу, но API-вызов инструмента, исполнение и ответ могут происходить разными сообщениями и событиями.

**Поиск:** Dialogue Agent формирует запросы → Source Adapter сохраняет исходники → мягкий отбор без дорогой LLM → переиспользование актуальных vacancy\_cards → при необходимости отдельный анализ LLM (карточка, теги и предварительная оценка за один содержательный проход) → Tag Resolver → атомарное сохранение через Storage → персональная оценка в context\_vacancies → выдача результатов. Подробная модель: [Database](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/1605696/Database+JobRadar).
