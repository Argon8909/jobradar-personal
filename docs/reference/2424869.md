**Статус:** согласованные технические принципы выполнения. Подробные HTTP/CLI-интерфейсы, retry policy и последовательности вызовов подлежат уточнению при проектировании инструментов.

## Выполнение поисковых задач

Каждый поиск создаёт независимую `search_tasks` со статусом и ссылкой на поисковый контекст; состав найденных вакансий — в `task_vacancies`. Исполнитель Task Manager не зависит от жизненного цикла UI. Состояния: pending, running, completed, failed, cancelled. Целевая архитектура допускает фоновое выполнение и события статуса. **В v0.1 выполняем поиск синхронно, без Celery/Redis/внешней очереди**; саму бизнес-логику поиска отделяем от Flask, чтобы позже добавить фоновый исполнитель без переписывания алгоритма.

## Контракт адаптера источника (концептуально)

| Операция | Назначение |
| --- | --- |
| `search` | Поиск по техническим параметрам площадки, возвращает найденные объявления |
| `fetch_details` | Получить полный текст и основные исходные метаданные |
| `check_status` | Проверить актуальность конкретного объявления перед повторным показом |

Это проект интерфейса, не готовые подписи методов. В v0.1 единственный действующий адаптер HH.ru с Playwright. Будущие источники вакансий — отдельные модули; различия в названиях полей и HTML остаются внутри адаптеров. Поиск автомобиля/недвижимости на Avito — не тот же доменный контракт вакансий.

## Обработка вакансий

Collector сохраняет исходник в vacancies, Task Manager делает мягкий первичный отбор по названию и явным параметрам. Для актуальной vacancy\_cards повторный разбор не нужен; иначе Vacancy Analyzer за один содержательный вызов DeepSeek возвращает карточку, теги (required/optional/mentioned, evidence) и при необходимости первичную контекстную оценку. Tag Resolver сопоставляет имена с tags/tag\_aliases, Storage сохраняет карточку, новые теги/синонимы/связи в контролируемой транзакции; оценки сохраняются в context\_vacancies. Новые карточки и теги не создаются отдельными Tool Calls на каждую колонку.

## Ошибки и выполнение

- Использовать единые машинные коды ошибок и сообщения для UI/LLM: недоступность источника, таймаут, сбой LLM, неверный структурированный ответ, конфликт данных, ошибка БД.
- Ошибка одной вакансии не должна автоматически портить ранее сохранённые карточки. Фиксировать статус задачи и достаточную диагностику для ручного тестирования.
- Предусмотреть лимиты на попытки, число LLM-вызовов, глубину Tool Calling и количество вакансий в одной задаче. Полный бюджетный механизм — целевой MVP, не v0.1.
- Повторное выполнение и идемпотентность обеспечить при сохранении исходника по (source, external\_id), карточки по vacancy\_id, тега и алиаса по нормализованному ключу с проверкой конфликтов.

## Уточнить перед реализацией

Точный протокол событий и статусов, точные эксплуатационные значения (после тестов) и конкретные коды ошибок. Полные схемы инструментов фиксировать в документе Tool Calling.

## Утверждено: выполнение поиска в v0.1

Поиск в v0.1 остаётся синхронной задачей Python (без внешней очереди), но Task Manager не связан с обработчиком Flask. При старте Python сразу передаёт интерфейсу статус «Поиск запущен», далее обновляет/хранит состояние `search_tasks`. По завершении результат направляется DeepSeek для формирования ответа пользователю. Сбор и анализ вакансий не расходуют лимит 20 Tool Calls диалогового агента; стартовые лимиты по вакансиям, LLM-вызовам и времени перечислены ниже и остаются предварительными. При временных ошибках максимум две безопасные автоматические повторные попытки.

## Предварительные эксплуатационные лимиты v0.1 — пересмотреть по результатам тестов

| Параметр | Стартовое значение | Пояснение |
| --- | --- | --- |
| Максимум исходных вакансий на одну поисковую задачу | `100` | Включая найденные ранее и дубликаты; ограничение на сбор |
| Максимум новых содержательных анализов вакансий DeepSeek за задачу | `30` | Повторно использовать актуальные vacancy\_cards, не тратить вызов на уже разобранные |
| Максимум длительности поисковой задачи | `10 минут` | Мягкий дедлайн: прекратить начало новых операций, корректно завершить текущую, сохранить частичные результаты и статус; не обещать мгновенную принудительную остановку Playwright/HTTP |
| Таймаут ожидания одного запроса DeepSeek | `60 секунд` | При временном сбое применить общую политику безопасного повтора, не превышать общий дедлайн задачи |
| Таймаут загрузки одной страницы источника | `30 секунд` | Для Playwright; отдельные сайты могут переопределить |
| Автоматические повторы временных сбоев | `2` | Ранее согласованный максимум, если операция безопасна для повторения |

Достижение лимита при наличии частичных результатов должно отражаться пользователю как неполное выполнение; нельзя помечать поиск полностью успешным без объяснения ограничения. Отдельный лимит стоимости/токенов для MVP и расширенная бюджетная диагностика проектируются позднее. Пересмотреть значения после первых реальных прогонов и замера скорости/стоимости.

## Принято: частичное завершение и проверка вакансий

Для задачи с неполной обработкой, но сохранёнными результатами устанавливать `search_tasks.state=completed`, `is_partial=true`, `stop_reason` с причиной (лимит, таймаут, CAPTCHA, ошибка источника и др.). Пользователю сообщать, что поиск неполный. Полный успех — `is_partial=false`, `stop_reason=NULL`. Не вводить новый статус задачи. Если результатов нет и произошёл сбой — `failed`.

При повторной оценке по новым критериям или профилю используем актуальную сохранённую карточку, не запрашивая сайт заново. Постоянно перепроверять HH.ru не нужно. Потенциальные будущие отклики потребуют отдельной точечной проверки вакансии непосредственно перед действием; функция откликов отсутствует в v0.1. Протокол отправки UI-статуса «Поиск запущен» оставить техническим выбором Codex, сохранив немедленное уведомление.
