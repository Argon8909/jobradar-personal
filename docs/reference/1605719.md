Идентификация и разделение данных. v0.1 запускается для одного пользователя, но физические связи допускают многих. Общий чат и выбор активного контекста реализуются через диалог.

**Уточнение:** типы приведены для целевой PostgreSQL-модели; метки «NULL (проект)» обозначают пока не утверждённые ограничения обязательности/значения по умолчанию. Для SQLite применяются совместимые физические типы.

## `users`

**Назначение:** Пользователь как владелец профилей, сессий и сообщений.

| Поле | Тип | Ключи / свойства | Смысл |
| --- | --- | --- | --- |
| `id` | BIGINT | PK, NOT NULL | Идентификатор пользователя |
| `name` | TEXT | NULL | Отображаемое имя |
| `created_at` | TIMESTAMPTZ | NOT NULL (проект) | Время создания |

**Связи и правила:** Родитель user\_profiles, user\_accounts, user\_sessions и messages. Пользователь v0.1 создаётся автоматически без регистрации.

## `user_accounts`

**Назначение:** Будущая привязка пользователей к каналам (VK/Telegram и др.).

| Поле | Тип | Ключи / свойства | Смысл |
| --- | --- | --- | --- |
| `id` | BIGINT | PK | ID привязки |
| `user_id` | BIGINT | FK users.id, NOT NULL | Владелец |
| `provider` | TEXT | NOT NULL | Канал / провайдер |
| `external_user_id` | TEXT | NULL (проект) | ID в провайдере |
| `status` | TEXT | NULL (проект) | Состояние связи |
| `linked_at` | TIMESTAMPTZ | NULL | Дата привязки |

**Связи и правила:** В v0.1 можно не наполнять. В дальнейшем уникальность пары provider + external\_user\_id и правила авторизации необходимо уточнить.

## `user_profiles`

**Назначение:** Профессиональная квалификация человека: профессия, категории, навыки, стаж и факты.

| Поле | Тип | Ключи / свойства | Смысл |
| --- | --- | --- | --- |
| `id` | BIGINT | PK | ID профиля |
| `user_id` | BIGINT | FK users.id, NOT NULL | Владелец |
| `profile_data` | JSONB | NULL (проект) | Структурированные сведения о профессии |
| `revision` | INTEGER | NULL (проект) | Версия данных для проверки актуальности оценок |
| `updated_at` | TIMESTAMPTZ | NULL (проект) | Последнее изменение |

**Связи и правила:** Каждый создаваемый профиль должен иметь минимум один поисковый контекст. Операция create\_profile атомарно создаёт user\_profiles и первый search\_contexts («Основной поиск») в одной транзакции; при ошибке откатываются оба. Дополнительные контексты создаются отдельно, удаление последнего не допускается. См. [контракт Tool Calling](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/2359317/Tool+Calling+v0.1). Один пользователь имеет N профилей. Водитель B и C могут быть одним профилем с двумя категориями или разными профилями по решению человека. Перед созданием LLM получает список похожих профилей и уточняет выбор.

**Общие правила JSONB:** версия контракта явно обозначается в JSON; имена свойств и enum — английские, пояснения и пользовательские значения могут быть русскими. `null` означает неизвестное/не указано, пустой массив — отсутствуют извлечённые элементы (не доказательство отсутствия требований). Отсутствующий необязательный ключ допускается, но приложение нормализует его согласно контракту. Оркестратор валидирует типы и значения перед сохранением. Внутренние версии редактирования `revision`/`criteria_revision` не являются версиями JSON-контракта.

### Контракт JSONB: `user_profiles.profile_data`

| JSON-путь | Тип | Обязательность | Описание |
| --- | --- | --- | --- |
| `schema_version` | integer | Да | Версия JSON-контракта, не редакция профиля |
| `profession` | string | Да | Основная профессия |
| `specializations[]` | string\[\] | Нет | Специализации |
| `experience[]` | object\[\] | Нет | Опыт по направлениям |
| `experience[].domain` | string | Да внутри объекта | Область деятельности |
| `experience[].years` | number/null | Нет | Подтверждённый стаж; null если неизвестен |
| `competencies[]` | string\[\] | Нет | Навыки пользователя, свободный текст |
| `qualifications[]` | object\[\] | Нет | Лицензии, допуски, сертификаты и категории |
| `qualifications[].type` | string | Да внутри объекта | Тип квалификации, например driving\_license, license, certificate |
| `qualifications[].name` | string | Да внутри объекта | Наименование |
| `qualifications[].details[]` | string\[\] | Нет | Категории, уточнения |
| `education[]` | object\[\] | Нет | Образование |
| `education[].level` | string/null | Нет | Уровень |
| `education[].field` | string/null | Нет | Область |
| `education[].qualification` | string/null | Нет | Квалификация |
| `education[].institution` | string/null | Нет | Учебная организация |
| `education[].year` | integer/null | Нет | Год окончания |
| `additional_attributes[]` | object\[\] | Нет | Редкие дополнительные характеристики |
| `additional_attributes[].key` | string | Да внутри объекта | Машинный ключ snake\_case |
| `additional_attributes[].value` | string/number/boolean/null | Да внутри объекта | Скалярное значение; не объект и не список |
| `additional_attributes[].description` | string | Да внутри объекта | Пояснение на языке пользователя |
| `notes` | string/null | Нет | Прочие исходные сведения о квалификации |

**Правила:** Квалификация пользователя, не условия поиска. Дополнительные характеристики допускаются лишь как редкие сведения; важные навыки сохраняются в competencies и qualifications. Каждая профессия использует одну схему.

## `search_contexts`

**Назначение:** Условия конкретного поиска, независимо от квалификационных сведений профиля.

| Поле | Тип | Ключи / свойства | Смысл |
| --- | --- | --- | --- |
| `id` | BIGINT | PK | ID контекста |
| `profile_id` | BIGINT | FK user\_profiles.id, NOT NULL | Связанный профиль |
| `title` | TEXT | NULL (проект) | Условное название |
| `criteria` | JSONB | NULL (проект) | География, формат, зарплата, ограничения и предпочтения |
| `criteria_revision` | INTEGER | NULL (проект) | Редакция критериев |
| `status` | TEXT | NULL (проект) | Активность |
| `created_at` | TIMESTAMPTZ | NULL (проект) | Создан |
| `updated_at` | TIMESTAMPTZ | NULL (проект) | Изменён |

**Связи и правила:** Каждый профиль имеет N контекстов; это не ограничено схемой 1:1. Выбор контекста только через диалог. Для целевого MVP возможны явно заданные исключения в criteria; механизм блокировки не реализуем в v0.1.

**Общие правила JSONB:** версия контракта явно обозначается в JSON; имена свойств и enum — английские, пояснения и пользовательские значения могут быть русскими. `null` означает неизвестное/не указано, пустой массив — отсутствуют извлечённые элементы (не доказательство отсутствия требований). Отсутствующий необязательный ключ допускается, но приложение нормализует его согласно контракту. Оркестратор валидирует типы и значения перед сохранением. Внутренние версии редактирования `revision`/`criteria_revision` не являются версиями JSON-контракта.

### Контракт JSONB: `search_contexts.criteria`

| JSON-путь | Тип | Обязательность | Описание |
| --- | --- | --- | --- |
| `schema_version` | integer | Да | Версия схемы criteria |
| `target_roles[]` | string\[\] | Нет | Направления поиска/похожие названия |
| `locations[]` | string\[\] | Нет | География, включая страны, регионы или города; правила кодирования уточнить для источника |
| `work_formats[]` | string\[\] | Нет | remote, hybrid, office; отсутствие не равнозначно запрету |
| `salary` | object/null | Нет | Зарплатные пожелания |
| `salary.min` | number/null | Нет | Нижняя граница |
| `salary.currency` | string/null | Нет | Валюта, ISO 4217 |
| `salary.strict` | boolean | Нет, default false | Жёсткая граница только по явному решению пользователя |
| `experience_level` | string/null | Нет | Желаемый уровень/стаж, если задан пользователем |
| `preferences[]` | object\[\] | Нет | Мягкие условия ранжирования |
| `restrictions[]` | object\[\] | Нет | Явные ограничения; не путать с блокировкой конкретной вакансии |
| `preferences[].attribute / restrictions[].attribute` | string | Да внутри объекта | Имя параметра поиска |
| `preferences[].operator / restrictions[].operator` | string | Да внутри объекта | prefer / exclude / require (уточняемый реестр) |
| `preferences[].value / restrictions[].value` | string/number/boolean | Да внутри объекта | Значение ограничения |
| `notes` | string/null | Нет | Дополнительные пользовательские пояснения |

**Правила:** Только критерии поиска; не копирует факты квалификации из профиля. Незаданная зарплата или её отсутствие у вакансии не служат автоматическим запретом. В целевом MVP исключение компаний/вакансий требует дальнейшего уточнения, в v0.1 отсутствует.

**Пример JSON**

```
{
  "schema_version": 1,
  "target_roles": [
    "Системный аналитик",
    "IT-аналитик"
  ],
  "locations": [
    "Россия"
  ],
  "work_formats": [
    "remote",
    "hybrid"
  ],
  "salary": {
    "min": 200000,
    "currency": "RUB",
    "strict": false
  },
  "experience_level": null,
  "preferences": [
    {
      "attribute": "domain",
      "operator": "prefer",
      "value": "EdTech"
    }
  ],
  "restrictions": [
    {
      "attribute": "work_format",
      "operator": "exclude",
      "value": "office"
    }
  ],
  "notes": null
}
```

## `user_sessions`

**Назначение:** Состояние текущего канала общения и выбранного контекста.

| Поле | Тип | Ключи / свойства | Смысл |
| --- | --- | --- | --- |

| `user_id` | BIGINT | FK users.id, NOT NULL | Пользователь |
| `active_context_id` | BIGINT | FK search\_contexts.id, NULL | Выбранный контекст, NULL в общем обсуждении |

**Связи и правила:** Одна сессия содержит много сообщений. При изменении active\_context\_id оркестратор проверяет, что контекст принадлежит текущему пользователю; не полагаться на один лишь FK.

## Принятые правила смены активного контекста

Создание `user_profiles` и первого `search_contexts` выполняется атомарно. После создания успешной пары приложение устанавливает `user_sessions.active_context_id` в ID первого контекста и уведомляет пользователя. Создание дополнительного контекста через `create_context` также приводит к его немедленной активации. При ошибке нельзя объявлять переход успешным. Возврат в общий диалог — `active_context_id=NULL` через `return_to_general`. Python проверяет владельца активируемого контекста.

Явные пользовательские команды создания/перехода не требуют повторного подтверждения; при инициативном предложении ассистента согласие проверяется в состоянии диалога, без новой таблицы подтверждений. После смены контекста набор доступных инструментов пересчитывается.
