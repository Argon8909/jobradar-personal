# Технические выходные контракты v0.1

Исполняемые схемы — `src/jobradar/analysis/contracts.py`.
`llm-outputs.json` — их экспорт для чтения, не второй редактируемый источник.
Основание: логическая модель Confluence 1605696 v9, дочерние страницы
1605719 v4 / 1802256 / 1802274 v6 и System Prompts 2293817 v1.
Входные определения 11 инструментов из 2490371 v1 остались без изменений.

## Planner

Возвращает `{search_queries, target_count}`. В search_tasks.search_queries
записывается только утверждённый JSON `{version, queries}`. Цель обработки
записывается в уже существующий search_tasks.target_count; null в LLM-ответе
означает отсутствие явно заданной пользователем цели и выбор настройки приложения.
Технический предел, цель и размер выдачи не смешиваются. Фильтры HH поддерживают
географию и формат; мягкая зарплата/опыт не превращаются в фильтры источника.

## Analyzer

За один вызов извлекает `card`, `tags` и `assessment`. Карточка соответствует
нормализованным колонкам vacancy_cards и контракту structured_data. Полный текст
не копируется в карточку, нормализованные навыки не записываются в additional_facts.
Карточка сохраняется независимо от пользователя, оценка — в context_vacancies.

Теги: category/name/requirement_level/evidence. Каждый evidence обязан быть
дословным фрагментом сохранённого текста объявления. При проверке допускается
различие только в пробельных символах; сохраняется найденная исходная цитата.
Неподтверждённый/некорректный тег пропускается с предупреждением, корректные
карточка и оценка сохраняются. Уровни: required/optional/mentioned.
SQL, новые теги и изменения профилей не являются инструментами анализатора.

Персональная оценка: decision и reasoning — текст, relevance_score — необязательное
число или null. Фиксированный продуктовый порог/шкала и обязательный enum решения
в исходной модели не утверждены; они не вводились. Решение и объяснение показываются
пользователю без автоматических откликов. Неизвестное не означает отсутствие навыка.

Режим assessment_only получает актуальную сохранённую карточку и теги вместо
нового разбора исходника. Используется тот же утверждённый промпт с отдельной
структурой входных данных; результат содержит только поля персональной оценки.

## Tag Resolver

Решение: use_existing/create_new/ambiguous и tag_id либо null. Существующий ID
может быть выбран только из предложенных кандидатов той же категории. Python
сначала ищет точное нормализованное совпадение в tags/tag_aliases. Известные
синонимы не расходуют LLM-вызов. При неоднозначности тег не объединяется автоматически;
в structured_data.uncertainties сохраняется пояснение, без создания ложного соответствия.
Ошибка схемы/сети/идентификатора при сопоставлении также пропускает только тег.
Корректные карточка и оценка сохраняются даже при исчерпании бюджета сопоставления.

Сохранение карточки, тегов, алиасов, связей и оценки — одна транзакция. При конфликте
или сбое прежняя карточка не разрушается. Обновление исходного хеша помечает прежние
персональные оценки устаревшими с сохранением reasoning; новых полей или таблиц нет.

## Свежесть и доступ

Актуальная карточка: source_hash совпадает с vacancies.content_hash и подходит
extraction_version. Актуальная оценка дополнительно требует совпадения revision
профиля и criteria_revision контекста. Сайт при чтении сохранённых результатов не
запрашивается. get_search_results/get_vacancy_details обновляют только персональную
оценку при актуальной карточке, в рамках отдельного ограниченного LLM-бюджета.
При невозможности переоценки старый результат помечается устаревшим и попадает
в отдельный список unassessed с причиной. Основной vacancies содержит только
актуально оценённые записи; известные несоответствия обязательным условиям отфильтрованы.
Ошибка переоценки одной карточки не прерывает остальные, пока есть бюджет.

Некорректный JSON/основная схема ответа допускает одно исправление тем же
специализированным LLM-контекстом. Обе попытки расходуют существующий TaskBudget.
Системные промпты и опубликованные схемы 11 инструментов не изменялись.
Этап, код ошибки, JSON Pointer и правило валидатора записываются в локальную
техническую диагностику; текст ответа модели в неё не записывается.

Доступ к задаче/деталям разрешён только в активном принадлежащем пользователю
контексте. Общая глобальная карточка сама по себе не даёт доступа к чужим результатам.
