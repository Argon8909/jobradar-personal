# JobRadar v0.3 — накопление вакансий и анализ рынка

**Статус:** предварительная концепция для обсуждения, 25.11.2026. Не техническое задание и не утверждённый состав релиза. Текущую v0.2 не менять до завершения этапа 4 и приёмки.

**Основной документ:** [Confluence — концепция v0.3](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/4784129).  
**Подробный сценарий:** [Регулярный сбор и нормализация по расписанию](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/6225928).  
**Требования:** [реестр FR-001–FR-042](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/1572885), [FR-042](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/5931009).  
**Предыдущая версия:** [Состав v0.2](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/4620289).

## Цель

Развить существующий персональный подбор в систему накопления и повторного использования данных вакансий: регулярный тематический сбор, экономичная нормализация доступных исходных атрибутов и облегчённый анализ рынка. Использовать Python, Playwright, Flask, SQLite, DeepSeek; **не** вводить PostgreSQL/Redis/Vector по умолчанию.

## Предварительное ядро

1. **Проверка HH-ID до открытия вакансии.** Извлекать ID из ссылок поисковой выдачи (уже поддержано адаптером), сравнивать с общей SQLite по `(source, external_id)`. Не скачивать повторно недавно проверенный известный ID без признаков изменений или контрольного срока. Сохранять признаки непроверенной актуальности.
2. **Лимиты на каждую поисковую фразу и на задачу.** Предусмотреть независимые `max_vacancies_per_query` и `max_vacancies_per_task`; отдельно учитывать новые полные скачивания, уже известные ID, контрольные проверки и обнаружения. Повторно обнаруженные ID не расходуют лимит **новых скачиваний**. В v0.2 100 — общий лимит всех поисковых фраз; исправление относится только к v0.3. Конкретные значения и семантику счётчиков утвердить после испытаний.
3. **Автоматический тематический сбор по расписанию.** По согласованному набору ключевых фраз, периоду, скорости и квотам; запуск, пауза, изменение, отключение, журнал запусков. Не требует профиля и массового DeepSeek. Не путать с [US-003 — персональным мониторингом и уведомлениями](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/1146883).
4. **Широкий охват без обязательного региона.** По умолчанию искать по ключевому слову без географического ограничения. При ограничении глубины выдачи по возможности делить по времени публикации, затем по регионам/другим доступным признакам. Дедуплицировать пересечения; фиксировать неполный охват. Не обходить CAPTCHA или ограничения HH.
5. **Отдельные режимы первичной загрузки и обновления.** Историческая выборка в пределах ресурсов; затем инкрементальный поиск новых публикаций с перекрывающимся периодом. Независимые бюджеты от персонального подбора, сохранение прогресса и контроль конфликтующих запусков.
6. **Повторные публикации и изменения.** HH-ID — ключ объявления; `published_at`, время последнего обнаружения `last_seen_at`, время последней полной проверки `last_content_checked_at`, статус и хеш смыслового содержания учитываются раздельно (названия полей предварительные). Для известного ID повторное чтение полного текста при изменении наблюдаемых метаданных, переоткрытии или истечении контрольного срока. **Смена даты без изменения текста не запускает DeepSeek**; если изменилось содержание, обновляется исходник и актуальность общей карточки. Различать уникальные ID, новые обнаружения и наблюдаемые повторные публикации, не удваивая количество вакансий в рыночной статистике.
7. **Дешёвая структурная нормализация.** Извлекать из доступных данных исходных вакансий профессию/название, работодателя, географию, дату, зарплату/валюту, формат, занятость, опыт и иные достоверные поля. Сохранять первоисточник, неизвестные значения и происхождение сведений. Не создавать универсальную LLM-карточку для каждого объявления. Точная схема SQLite — отдельное решение.
8. **Облегчённый анализ рынка — [FR-042](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/5931009).** Количество уникальных объявлений, распределения по времени/регионам/форматам, зарплаты и опыт по действительно доступным полям. Навыки и сравнения — при доказанном качестве извлечения. SQL рассчитывает показатели, LLM интерпретирует. В каждом ответе указывать период, объём выборки, пропуски данных и ограничения охвата; не выдавать выборку за весь рынок.

**Поток:** Collector → сохранение исходника и дешёвая нормализация → общая SQLite → персональный подбор **или** анализ рынка. LLM-карточки и контекстные оценки создаются по необходимости отдельно.

## Дополнительные небольшие функции — только после оценки объёма

- Минимальные выбираемые инструкции для LLM ([FR-038](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/4063233)) без RAG и автоматического накопления.
- Сохранение скриншотов и признаков ошибок HH как часть [FR-036](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/3276801), без отдельного vision-агента.
- Ограниченный импорт резюме (FR-003).
- Светлая/тёмная тема ([FR-041](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/4390916)), если не завершена в v0.2.
- Индексы/FTS5 только по результатам измерений.

## За границами предлагаемой v0.3

PostgreSQL, Redis, распределённая очередь и полное [FR-040](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/4423684), embeddings и [FR-039 — SQL + Vector](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/4653062), pgvector, RAG, развитые агенты и мессенджеры, обязательный VPS. Эти направления сохранены в [общем банке гипотез](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/6094849) и не исключены из **целевого MVP** — лишь не включены в предварительную лёгкую v0.3.

## Проверки перед утверждением

- Установить, какие метаданные видны в HH-выдаче без перехода в карточку и что происходит с HH-ID и датой при переоткрытии, поднятии и правке.
- Проверить, работает ли деление по временным интервалам, где заканчивается доступная пагинация и какие реальные ограничения источника.
- Утвердить семантику лимитов на фразу, задачу, новые скачивания и накопительный сбор.
- Проработать изменения SQLite и разделение `content_hash` и даты; не создавать повторных платных карточек только из-за метаданных.
- Проверить поведение расписания при выключенном локальном ПК и частичных сбоях.
- Согласовать минимальный набор доступных полей для статистики без платной массовой обработки.
