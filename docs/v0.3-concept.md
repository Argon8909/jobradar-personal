# JobRadar v0.3 — концепция архитектурного развития

**Дата фиксации:** 20 ноября 2026 года.  
**Статус:** рабочая концепция. Ни состав релиза, ни реализация, ни сроки не утверждены.  
**Главный документ:** [Confluence — JobRadar v0.3, концепция развития архитектуры](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/4784129).  
**Предыдущий этап:** [Состав и ограничения v0.2](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/4620289).

## Цель

После реализации в v0.2 многоступенчатого широкого поиска на SQLite рассмотреть переход к более масштабируемому хранению и очередям, а также добавить семантический поиск вакансий **наряду** с обычными SQL-фильтрами. Принцип диалогового взаимодействия остаётся неизменным: пользователь разговаривает с JobRadar как с консультантом, а не заполняет обязательные фильтры в форме.

## Кандидаты для v0.3

| Направление | Предварительный объём | Решение |
|---|---|---|
| PostgreSQL | Серверное хранение, миграция данных SQLite, проверка целостности и резервного восстановления | Проектируется, не обязательно до измерения нагрузки |
| Redis | Внешняя очередь/работники взамен или поверх локальных заданий SQLite; долговременное состояние — в БД | Проектируется, библиотека и целевая модель неизвестны |
| SQL + Vector | Взаимодополняющий поиск: точные атрибуты/ограничения через SQL, смысловые совпадения — через embeddings | Гипотеза, требуется оценка |
| pgvector | Кандидат для хранения embeddings в PostgreSQL вместо отдельной векторной СУБД | Не утверждено |
| Локальные embedding-workers | Векторизация исходных вакансий и, при необходимости, нормализованных карточек без платной генеративной LLM | Эксперимент, зависит от CPU/RAM |
| VPS / гибридное размещение | Инфраструктура, безопасность, доступ к данным, размещение браузера Playwright | Исследовать по фактическим ограничениям |

## Принципы архитектуры

1. **SQL и векторы — параллельные механизмы.** Отсутствие embeddings не блокирует SQL/FTS-поиск, а косинусная близость не доказывает соответствие зарплате, категории прав, месту, графику или обязательным навыкам.
2. **Текущий конвейер остаётся:** Collector → сохранённый исходник → локальный отбор → создание общей карточки по потребности → персональная оценка → диалоговая выдача. Изменение поведения фиксируется в отдельно версионируемом алгоритме, а не автоматически при выходе v0.3.
3. **Миграция данных — проверяемая операция.** Не удалять исходную SQLite, переносить все связи, обеспечивать резервную копию и контроль целостности.
4. **Очередь не равна источнику истины.** Состояния обработки и исходники должны восстанавливаться после сбоев Redis/работников.
5. **Embeddings — производный индекс.** Оригинал и нормализованная карточка сохраняются. Модель, версия, шаблон, источник и хеш учитываются, чтобы векторы можно было пересчитать, не повторяя без необходимости DeepSeek.
6. **Наращивание ресурсов обосновано измерениями.** Сравнить SQL/FTS, Vector и гибридный поиск на 300–500 вакансиях; измерять recall, качество top-N, CPU, RAM, время, нагрузку и стоимость одной полезной подборки.

## Что не входит автоматически

Полноценная RAG-память агента, reranking, Honcho/Hindsight/OpenViking, мессенджеры, vision-диагностика, коммерческая многопользовательская версия, вся облачная инфраструктура или обязательное наличие pgvector в первой сборке v0.3. Это кандидаты на отдельное обсуждение и приоритизацию. Текущая v0.2 по-прежнему ориентирована на SQLite + WAL + FTS5 и фоновую обработку без Redis.

## Следующий шаг

После проверки v0.2 по качеству отбора и эффективности создать отдельный **«Состав и ограничения v0.3»** со ссылками на утверждённые FR/NFR и версии алгоритмов. Затем уточнить контракт БД/очереди, миграции, критерии приёмки и план выпуска. **Пока код, схема и существующие требования не меняются.**
