# JobRadar v0.2 — второй этап

Основание: пользовательское задание этапа 2, актуальные Confluence
[алгоритм 1.0](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/3899393)
v4, [состав v0.2](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/4620289)
v5 и [FR-037](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/3670017) v1.

## Реализация

1. Выборка актуальных общих карточек, предварительный фильтр, повторное использование
   актуальной контекстной оценки или assessment_only. Новое извлечение не выполняется.
2. Выборка без актуальной карточки (включая устаревшие), ранжирование и общий фильтр
   до extract_and_assess. Снимок ID не пропускает строки при изменении карточек.
3. HH-исходники сохраняются порциями; после сохранения доступной порции выполняется
   та же маршрутизация, затем продолжается сбор. Внутренняя порция — до 10 исходников,
   это ограниченный список в памяти текущего запроса, а не долговременная очередь.
4. Лимит HH учитывает уникальные (source, external_id) за всю задачу. Локальные
   кандидаты его не расходуют; общая дедупликация предотвращает повторное чтение
   тех же HH-ID в разных запросах. Поддержка work_formats у адаптера сохранена,
   но серверная политика алгоритма по умолчанию передаёт только text и areas.
5. Предел новых анализов и общий лимит LLM откладывают дальнейшие платные операции,
   сохраняя возможность сбора до лимита HH/дедлайна. Конкретный отказ анализа
   не удаляет исходник и не останавливает оставшийся поток. Цель результатов
   не прерывает сбор и не считается числом подходящих вакансий.
6. search_results в NDJSON передаёт заменяемый снимок готовой подборки со стабильными
   vacancy_id. Временная подборка заменяется в одной области чата, затем заменяется
   итоговой историей. Диалоговый агент не повторяет итоговый список свободным текстом.
7. При новом исходнике устаревший результат убирается из промежуточного снимка;
   подтверждённо закрытые записи не выдаются как доступные. Их карточки не удаляются.

## Консервативный отбор

Формат/география/строгая зарплата готовой актуальной карточки проверяются до
персональной оценки. Сырой текст проверяется только по надёжно распознаваемым
фактам (например, отдельное поле «Формат работы: офис»), а не по случайному
упоминанию офиса в обязанностях. Подтверждённое закрытие также является основанием
отбора. Неизвестность, отсутствие ключевого слова, другое название роли и нулевой
балл ранжирования не являются окончательным отказом. Исключённые исходники остаются
доступными другим контекстам. Неполное чтение не стирает уже сохранённый полный текст;
запись без описания не передаётся на извлечение как полная.

## Сохранённые ограничения

Схема SQLite, контракты 11 команд и config/v0.1.json не менялись. По-прежнему:
100 уникальных HH-обнаружений, 30 попыток нового анализа, 100 специализированных
LLM-вызовов, 600 секунд, цель 20. Ошибки и повторные вызовы входят в прежние бюджеты.
extract_and_assess не разделён на два обязательных вызова. В его инструкции добавлено
только требование независимости общих card/tags от профиля; риск смысловой зависимости
результата живой модели остаётся предметом проверки третьего этапа.

Выполнение остаётся синхронным: во время одного LLM-вызова браузер не получает
следующие страницы. Сырые записи переживают перезапуск, но автопродолжение анализа
и восстановимая очередь не добавлены. Существующие транзакции, разрешения,
обработка CAPTCHA и раздельная техническая панель сохранены.

## Диагностика и проверки

Добавлены отдельные счётчики HH-обнаружений, повторов, полных/неполных чтений,
сохранений, локальных кандидатов, отсева, отложенных и доступных к показу результатов.
Сохранение включает обновление уже известной записи, не только вставку новой.
Оценено не означает «подходит»: доказанные нарушения не включаются в выдачу.
coverage показывает выполненные запросы/этапы и ограничение охвата; при лимите,
ошибке источника или дедлайне не утверждается, что HH просмотрен полностью.

Проверки:

```text
python -m unittest discover -s tests/v01 -q
python -m unittest discover -s tests/v02 -q
python -m unittest discover -s tests/browser -q
python -m unittest discover -s tests -q
python -m pip check
```

HH/DeepSeek в тестах заменены контролируемыми ответами; браузерные сценарии
используют Chromium, локальный HTTP-сервер и перехваченные тестовые страницы.
Живые запросы HH/DeepSeek не выполняются. Старые ожидания изменены только для
нового смысла квоты HH, политики фильтров источника и появления промежуточных событий.

Итог проверки: 141 тест v0.1, 21 приёмочный тест v0.2, 13 браузерных сценариев
Chromium и 9 тестов прежнего прототипа — всего 184, все успешно. pip check —
конфликтов зависимостей нет; git diff --check — без замечаний.

## Передача третьему этапу

- Возраст публикации 30 дней, извлечение даты и её корректная нормализация.
- Разовые/сохранённые периоды, календарные месяцы, явное отключение и приоритеты.
- Отдельный редактируемый файл поисковой конфигурации.
- Полная доработка управляющих промптов и сценариев backlog, география без
  сгенерированных HH-ID, проверка качества с живой моделью.
- Измерения времени/расходов, распределения охвата между запросами, точности
  простого отбора и достаточности результата. Фиксированные пороги «подходит»
  и правила раннего завершения в этом этапе не вводились.
