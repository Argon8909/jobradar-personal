Этап 4: [техническая проверка и исправления](v0.2-stage4.md) выполнены;
[локальная приёмка на Windows](v0.2-local-acceptance.md) ожидается.
**Основной документ:** [Состав и ограничения v0.2 (Confluence)](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/4620289).  
**Алгоритм отдельно:** [Поисковый алгоритм 1.0](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/3899393).  
**Основа:** действующая v0.1 на Python, Playwright, SQLite, DeepSeek и Flask.

## Цель и границы

Улучшить поиск и экономичность анализа существующей v0.1 при минимуме архитектурных изменений. JobRadar остаётся **диалоговым консультантом**; требования к работе выявляются из беседы, а не через обязательные формы/ползунки. Новая PostgreSQL, Redis, таблицы фактов, постоянная очередь и embeddings не требуются.

### Поставляемое поведение

1. LLM составляет поисковый план из профессии, навыков, допустимых смежных направлений и ограничений пользователя.
2. **В первую очередь** искать среди **актуальных готовых универсальных карточек** `vacancy_cards`. Подходящие карточки сразу передавать на контекстную оценку, а существующие актуальные оценки переиспользовать. DeepSeek **не пересоздаёт** актуальную карточку.
3. Затем выбирать по текущему поисковому контексту среди сохранённых исходников `vacancies`, для которых **нет актуальной карточки**. Программный отбор — по доступным полям и тексту, без LLM. Не отбрасывать неопределённые значения как несоответствия.
4. Collector через Playwright получает доступные вакансии HH.ru по ключевым словам и, если нужно, региону; сохраняет исходники в общую SQLite. **Первый предел — 100 уникальных вакансий на задачу**, редактируется в конфигурации. Вновь сохранённые исходники включать в этот же программный отбор, в том числе **до завершения всего сбора**, если уже доступны. При наличии актуальной карточки возвращаться к шагу 2.
5. Кандидаты с актуальной карточкой идут прямо на контекстную оценку. Кандидатам без актуальной карточки DeepSeek создаёт или обновляет общую карточку и теги в пределах отдельно настраиваемого лимита, затем выполняется персональная оценка в `context_vacancies`.
6. По мере готовности показывать пользователю результаты и фактическое состояние; завершение сбора, завершение анализа и достижение целевого числа результатов — разные события. Правила дополнительного прохода и конечной остановки остаются частично открытыми.

**Важный нюанс:** лимит 100 вакансий HH, лимит новых LLM-карточек и целевое число результатов — **три независимых параметра**. Первые испытания нужны для оценки скорости и эффективности. Если пользователь решит, лимит сбора можно увеличить до 500/1000 без изменения алгоритма.

## Программный фильтр

Сначала использовать **существующие** поля `vacancies` и текст: ID/источник, название, работодатель, содержание, даты и уже доступные признаки; при работе с готовыми карточками — их структурированные поля и теги. В тексте допустим простой поиск профессиональных слов/навыков, синонимов, признаков требований. Жёстко исключать только проверенное несоответствие явно жёсткому критерию; неизвестные факты остаются кандидатами.

**Не требуются** таблица `vacancy_facts`, полная нормализация из HTML, обязательный FTS5, новая схема карточки или самостоятельный LLM-классификатор на первом этапе. Если текущего фильтра окажется недостаточно, расширять его после измерений, не усложняя заранее.

## Техническое исполнение

- **БД:** оставить действующую SQLite и существующие таблицы `vacancies`, `vacancy_cards`, `context_vacancies`, `search_tasks`, `task_vacancies`, теги. Не менять логическую модель. Безопасные индексы возможны только по результатам измерений.
- **Код:** в первую очередь изменить порядок операций `SearchService`, существующий Collector/HHAdapter и консервативный фильтр. Сохранение исходников должно предшествовать DeepSeek. Реализация **не обязана** запускать независимые фоновые процессы; допустима порционная обработка в текущей задаче.
- **Конфигурация:** вынести лимиты сбора, анализа, времени и целевого числа результатов в редактируемый файл с ясными именами; сохранить совместимость с существующим загрузчиком конфигурации. Первое утверждённое значение — 100 вакансий HH; другие лимиты определяет текущая проверенная конфигурация или последующее решение.
- **Надёжность:** записанные исходники остаются после перезапуска, но автоматическое продолжение незавершённого LLM-анализа без очереди не гарантируется. Сохранить обработку ошибок, диагностику и ручную проверку CAPTCHA из v0.1.
- **Промпты:** исправить поведение Dialogue Agent и Search Planner по [существующему backlog](backlog/prompt-behavior.md); не навязывать новые профили/контексты, не придумывать опыт, объяснять фактический поиск.

## Критерии приёмки

1. Актуальные готовые карточки отбираются и оцениваются без повторного извлечения.
2. Старый исходник без карточки может пройти программу отбора, получить общую карточку и оценку.
3. Новая вакансия HH может попасть в ту же подборку, когда доступна, не дожидаясь всей партии.
4. Лимит 100 настраивается, не означает 100 вызовов DeepSeek.
5. Неизвестные значения не отбрасываются необоснованно.
6. Ошибка DeepSeek не уничтожает уже сохранённые исходники; отсутствие автоматического восстановления анализа явно допустимо.
7. Диалог не подменяется формой настройки; прогресс и причина частичного завершения не искажаются.

## Открытые вопросы для первого экспериментального прогона

Сколько новых карточек создавать; как распределять 100 вакансий между несколькими поисковыми фразами; при каких условиях закончить подборку; когда делать дополнительный проход по накопленной базе; способ порционной выдачи результатов при текущем устройстве приложения. Это **частично решённые** вопросы, не основания внедрять новую инфраструктуру. Начать с 100, затем протестировать на большем объёме для оценки полноты.

## Возраст публикации и доступность вакансий (утверждено для v0.2)

Полное правило: [Поисковый алгоритм 1.0](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/3899393).

- **По умолчанию** рассматривать вакансии с датой публикации не старше **30 календарных дней**; использовать `vacancies.published_at`, не дату скачивания в JobRadar.
- Правило распространяется **одинаково** на актуальные готовые карточки, старые исходники без карточек и новые записи HH; применяется **до вызова DeepSeek** для создания карточки.
- Настраиваемое переопределение в диалоге: срок для отдельного поиска; при явном запросе на постоянное изменение — сохранение в поисковом контексте. Приоритет: **текущая поисковая задача → контекст → глобальная настройка (30 дней)**. Допускается явное отключение возрастного фильтра.
- Старые записи **не удалять** из SQLite и не блокировать глобально; при расширении окна они снова доступны. Если дата отсутствует/неопределённа, не отбрасывать автоматически.
- **Возраст публикации и доступность — разные свойства.** Подтверждённо закрытые объявления не рекомендовать как действующие; отсутствие свежей проверки не считать доказательством актуальности. Не запускать массовую повторную проверку каждого исходника.
- Если свежих вакансий недостаточно, предложить пользователю расширить срок, но **не расширять автоматически**.
- В `config/search-v0.2.json` используется `vacancy_max_age_days: 30`; null отключает глобальный предел. Схема SQLite не меняется.

Тесты: 31-дневная публикация исключается при лимите 30, хотя скачана сегодня; более широкий срок возвращает сохранённую вакансию; дата отсутствует — исключения нет; разовое условие не меняет контекст; закрытая вакансия не показана как доступная; фильтр по дате не вызывает DeepSeek.

## Уточнения Collector, HH-адаптера, DeepSeek и лимитов (24.11.2026)

**Источник истины:** [Поисковый алгоритм 1.0](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/3899393) и [Состав v0.2](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/4620289).

1. **Адаптер HH.ru сохраняет функциональность.** Нельзя удалять уже поддерживаемые фильтры, включая формат работы; предусмотреть возможность расширять набор доступных параметров источника. **Текущий алгоритм** по умолчанию включает только ключевые слова и регион. Кто и по каким правилам включает дополнительные фильтры (Search Planner / пользователь / LLM), пока остаётся открытым вопросом; LLM не может произвольно менять набор фильтров в обход проверок оркестратора.
2. **Предел 100 уникальных вакансий HH на поисковую задачу** — отдельный лимит сбора. Локальная база и её готовые карточки не расходуют этот предел. Обнаруженные, успешно сохранённые, повторно встреченные и ошибочные объявления учитывать раздельно, чтобы не смешивать лимит сбора и полноту обработки.
3. **Очередность:** сначала актуальные карточки (без повторной структуризации), затем сохранённые вакансии без актуальной карточки, параллельно/порциями — новые исходники HH.
4. **Предварительный фильтр обязателен перед DeepSeek** для исходников без актуальной карточки, в том числе для только что загруженных HH. Неотсекаемые неизвестные факты не превращать в отрицательный результат.
5. **Текущий DeepSeek-вызов `extract_and_assess` можно сохранить** для новых карточек; универсальная карточка и персональная оценка логически и в БД разделены. Актуальную карточку не создавать повторно, при необходимости — `assessment_only`.
6. **Три независимых параметра:** лимит сбора HH; лимит новых платных анализов/карточек; целевое число результатов. Достижение цели по результатам не равно полному просмотру HH. Досрочную остановку сбора по достаточности результатов отдельно не утверждали; первый прогон должен честно показывать частичный охват.

**Изменения схемы SQLite для перечисленного не обязательны.** Тесты должны проверять поведение адаптера без удаления поддерживаемых фильтров, предварительное отсечение до LLM, повторное использование карточек и раздельный учёт лимитов.
