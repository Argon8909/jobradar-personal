# JobRadar v0.2 — начало разработки концепции

Дата фиксации: 18 ноября 2026 года.
Статус: открытый черновик концепции, основа будущего технического задания.
Пользователь продолжает проверять текущую v0.1; её вопросы и наблюдения ещё будут
дополнять этот документ. Состав v0.2 и технические контракты пока не заморожены.
Реализация v0.2, подключение Redis и изменение действующих промптов не начаты.
Разработка концепции продолжается в ветке `jobradar-v0.2`, созданной от
`jobradar-v0.1`. Добавлены направления интерфейса, мессенджеров, PostgreSQL и
постепенного перехода с локального компьютера в облако.

## Направление 1. Управляющие промпты и качество поиска

Использовать [существующее задание](backlog/prompt-behavior.md), не создавать
параллельный набор противоречащих требований. Доработать совместно Dialogue Agent,
Search Planner и технические инструкции распознавания намерения.

Поиск должен учитывать квалификацию, задачи и допустимые смежные роли. Новое
ключевое слово не требует нового профиля/контекста. Вопрос о прошлом поиске
получает объяснение по фактическому плану и диагностике. Явно ограниченный запрос
пользователя не расширяется самовольно; квалификации не придумываются.

Проверить на обновлённой v0.1, какие наблюдения первоначальной сборки ещё
воспроизводятся. Узкий план запросов и остановку до остальных запросов из-за
бюджета различать по данным, а не по одному виду выдачи.

## Направление: экономичная воронка подбора и общая база карточек (FR-037)

Основной источник требований: [FR-037 в Confluence](https://arkadijgoncarov.atlassian.net/wiki/spaces/JOBRADAR/pages/3670017/FR-037).
Согласовано для целевого MVP; проектируем в рамках v0.2, но состав выпуска пока не заморожен. Не считать реализованным.

Сначала использовать актуальные общие карточки, затем расширять выборку новым браузерным сбором HH.ru. Сохранять обнаруженные исходные вакансии независимо от интереса текущего пользователя. Среди вакансий без карточек выполнять дешёвый, осторожный программный отбор; потенциально интересные — передавать LLM для создания универсальной карточки. Карточка и теги общие, персональная оценка привязана к поисковому контексту. Неподходящая одному пользователю вакансия остаётся доступной для другого.

Критерии приёмки и открытые вопросы о поиске по необработанным исходникам, полноте метаданных, индексировании, приоритизации, стоимости и конкуренции — в FR-037; не дублировать контракт здесь. При проектировании очереди Redis разделить универсальную структуризацию и персональное оценивание и не создавать по умолчанию LLM-задание на каждый собранный исходник.

## Направление 2. Независимый сбор и анализ, очередь на Redis

Направление для v0.2: использовать Redis для очереди задач анализа.
Конкретная библиотека работников, способ запуска и настройки надёжности пока
не выбраны. Это изменение ограничения v0.1 «синхронно, без очереди» относится
именно к будущей версии; текущий контракт v0.1 не переписывается задним числом.

Предполагаемый поток:

1. Сборщик Playwright читает страницу и надёжно сохраняет исходное объявление в БД.
2. На сохранённую версию объявления создаётся задание анализа в очереди Redis.
3. Обработчик забирает задание, вызывает DeepSeek, сохраняет карточку, теги и
   персональную оценку. Пока он ждёт модель, сборщик может читать следующие страницы.
4. Интерфейс отдельно показывает ход сбора и обработки, готовые результаты и ошибки.

База остаётся долговременным источником исходников и результатов. Redis не должен
быть единственным местом, где можно узнать о необработанной вакансии. Очередь
по возможности передаёт ссылки/идентификаторы, а не копии резюме и полных объявлений.

Для технического задания проработать:

- Состояния заданий, связь с поиском, версией исходника, профилем и критериями.
  Разделить общее извлечение карточки и персональную оценку, чтобы не дублировать
  анализ одной версии для разных контекстов и не смешивать оценки пользователей.
- Надёжный переход «сохранено в БД → поставлено в очередь», подтверждение обработки
  после сохранения результата, восстановление после перезапуска/потери Redis.
  Не обещать единственную доставку; повторная доставка не должна создавать дубли.
- Ограничение опережения сборщика, числа работников, объёма очереди, повторов,
  LLM-вызовов и расходов. Определить отдельно длительность сбора и обработки:
  старый единый дедлайн нельзя механически переносить в фоновые задачи.
- Отмену поиска, обработку ожидающих и уже взятых заданий, изменение критериев
  во время обработки, сохранение доступных результатов при отказе одного компонента.
- Порядок покрытия нескольких поисковых вариантов, чтобы первый не забирал весь
  бюджет; измерение времени страницы, ожидания в очереди, LLM и сохранения.
- Работу БД при конкурентных обращениях и короткие транзакции. Целевое направление
  v0.2 — PostgreSQL (см. направление 6). Все новые состояния/таблицы оформить
  в контракте v0.2; порядок перехода согласовать с вводом очереди.
- Удобный локальный запуск на Windows: выбрать и описать установку Redis,
  запуск/остановку приложения и работников, проверку готовности и восстановление.

Ключевой проверочный сценарий: при задержанном ответе DeepSeek несколько следующих
объявлений уже сохранены; после перезапуска ожидающие задания доступны, дубли
результатов не возникают, интерфейс показывает отдельные счётчики этапов.

## Направление 3. Модуль визуальной диагностики проблем

Назначение: зафиксировать и объяснить нестандартную блокирующую ситуацию при сборе.
Предварительные события: CAPTCHA, требование входа, ограничение доступа, неожиданный
переход, отсутствие ожидаемого содержимого, подозрительная выдача, повторные таймауты.
Нужны критерии срабатывания и подавление повторных уведомлений; обычный пустой поиск
не должен автоматически превращаться в инцидент.

Пожелания пользователя, которые включаем в проработку:

- Сделать скриншот страницы при инциденте; связать его с поиском, источником,
  временем, URL, этапом и кодом проблемы. Для исчезающих ситуаций захватывать его
  до закрытия страницы, когда это технически возможно.
- Сохранить снимок. Вариант «байты в БД» или «файл/хранилище и ссылка в БД»,
  срок хранения, очистку и ограничения размера ещё выбрать.
- Поддержать маршруты «администратору», «нейросети», «обоим» и только локальное
  сохранение. Конкретный мессенджер/получатель ещё не выбран. Доставка через адаптеры,
  с понятным статусом и ограниченными повторами при ошибке.
- Настраивать события, адресатов, маршруты и режим реакции отдельным текстовым
  конфигурационным файлом; предполагаемый формат JSON, окончательная схема впереди.
  Секреты интеграций хранить отдельно от публикуемой конфигурации.
- Использовать отдельный текстовый диагностический промпт и отдельный LLM-контекст,
  не смешивая снимки и инструкции диагностики с чатом пользователя и оценкой вакансий.
  Возможные результаты: тип проблемы, наблюдаемые признаки, неопределённость,
  рекомендуемое действие и необходимость участия человека.
- Выбрать провайдера/модель, действительно принимающую изображения. Поддержку
  изображений текущей текстовой моделью DeepSeek не считать установленной;
  возможности и условия выбранной модели проверить при выборе интеграции.
- Предусмотреть управление внешней отправкой и маскированием чувствительных
  областей снимка. Не прикладывать cookies, токены или ключи к диагностическому запросу.

Режимы реакции, доступные действия и полномочия диагностики необходимо определить
в ТЗ. Пока не согласованы самостоятельное управление браузером по ответу модели
или автоматический обход блокировок. Существующее ручное прохождение CAPTCHA
сохранить как рабочий сценарий. Отказ vision-модели/уведомлений не должен уничтожать
уже сохранённые вакансии и диагностические материалы.

Ключевой проверочный сценарий: тестовая блокировка создаёт один связанный инцидент
со снимком, выбранные получатели получают его и результат анализа; отказ доставки
виден, повторные события не создают бесконечную рассылку.

## Направление 4. Тёмная и светлая темы интерфейса

Пользователь предпочитает тёмную тему. Требования для проработки:

- Поддержать тёмную и светлую темы с явным переключателем. Для новой установки
  ориентир — тёмная тема по умолчанию; сохранённый выбор пользователя имеет приоритет.
- Сохранять выбор между посещениями и применять его до показа основного интерфейса,
  чтобы при открытии тёмной темы не появлялась яркая светлая вспышка.
- Темизировать весь интерфейс: чат, поля, кнопки, результаты, диагностику,
  уведомления, ошибки и состояния ожидания. Проверить читаемость, фокус клавиатуры
  и мобильный экран в обеих темах.
- Обсудить режим «как в системе» как дополнительную возможность; он не должен
  отменять явный выбор пользователя. Способ хранения настройки в локальном
  и облачном режимах определить в ТЗ.

Проверка: выбрать тему, перезагрузить страницу и перезапустить приложение;
выбор сохраняется, элементы читаемы, светлая вспышка при тёмной теме отсутствует.

## Направление 5. Интеграции с мессенджерами

Заложить расширяемую возможность интеграций. Конкретный мессенджер и обязательный
объём первой интеграции ещё не выбраны; наличие готового двустороннего бота во всех
мессенджерах не является уже утверждённым требованием v0.2.

Разделить два сценария:

- Исходящие уведомления: готовность/частичное завершение поиска, ошибки,
  необходимость участия пользователя, снимки и результаты визуальной диагностики.
- Возможный следующий этап: диалог и команды из мессенджера с доступом к своим
  профилям, контекстам и результатам. Отдельно определить набор команд и права.

Общую бизнес-логику сохранить вне веб-интерфейса и адаптеров конкретного канала.
Сообщения диагностики использовать через тот же механизм доставки. Настройки
каналов и получателей отделить от секретов, предусмотреть включение/отключение,
повторы и защиту от повторной отправки одного события.

Входящие команды потребуют привязки аккаунта мессенджера к пользователю JobRadar,
проверки подлинности события и тех же правил разрешения действий, что в веб-чате.
Способ доставки (опрос или webhook), ограничения вложений, формат результатов
и хранение общей истории определить при выборе первого канала.

Проверка минимальной реализации: зарегистрированный адаптер доставляет событие
нужному получателю; отказ канала виден и не прерывает поиск; замена адаптера
не требует переписывать поиск или анализ вакансий.

## Направление 6. PostgreSQL и постепенный переход в облако

Целевое направление — переход от локального приложения на компьютере пользователя
к варианту развёртывания в облаке и от SQLite к PostgreSQL. Это несколько этапов,
а не одномоментное требование перенести всё. Провайдер облака пока не выбран.

Для будущего ТЗ:

- Подготовить доступ к хранилищу через явные границы модулей и миграции схемы.
  PostgreSQL должен поддерживать конкурентную работу приложения и обработчиков.
  Не переносить SQLite-специфичный SQL механически; проверить транзакции,
  ограничения, JSON-поля, индексы и сопоставление тегов.
- Спроектировать перенос существующих данных v0.1 в PostgreSQL: профилей,
  контекстов, истории, исходников, карточек, тегов, оценок и поисковых задач.
  Предусмотреть резервную копию, проверку связности/полноты и возможность
  возврата к исходной установке. Не требовать удаления рабочей SQLite-базы.
- Сначала проверить локальный запуск приложения, PostgreSQL и Redis;
  затем подготовить воспроизводимое облачное развёртывание. Длительность поддержки
  SQLite после перехода и конкретный механизм запуска ещё определить.
- Вынести адреса БД, Redis, файлового хранилища и провайдеров в конфигурацию
  окружения. Скриншоты и другие файлы не должны зависеть от случайного локального
  пути процесса; способ хранения и резервного копирования выбрать отдельно.
- Перед доступом из интернета определить аутентификацию, авторизацию, HTTPS,
  управление секретами и сессиями. Нынешний локальный режим не публиковать простым
  открытием порта. Полноценный многопользовательский продукт пока не включён
  автоматически — его границы требуют отдельного решения.
- Отдельно решить размещение Playwright и управление браузерным профилем HH.
  В облаке нет привычного видимого окна на компьютере пользователя: нужен
  доступный сценарий ручного входа/проверки либо вариант с локальным сборщиком
  и облачными остальными компонентами. Снимок и сообщение в мессенджер сами
  по себе не решают задачу взаимодействия с CAPTCHA. Получение HH-данных
  остаётся через Playwright; использование API не вводится.
- Предусмотреть остановку, обновление и восстановление компонентов, наблюдение
  за очередью, резервные копии БД и проверку восстановления.

Проверка: данные тестовой копии v0.1 перенесены без потери связей; одинаковый
основной сценарий работает с PostgreSQL локально и в выбранной облачной схеме;
пользователь может пройти необходимую проверку HH при выбранном размещении сборщика.

## Итерации, сборки и выпуск v0.2

Итерация — этап работы, версия — обозначение поставляемого состояния продукта.
Несколько итераций могут готовить один выпуск `0.2.0`. После каждого коммита
или итерации номер версии повышать не обязательно.

Предлагаемый порядок ниже — рабочий план, не зафиксированный календарь или
обещание включить все возможности в первый промежуточный выпуск:

| Этап | Результат для проверки |
|---|---|
| 1. Основа ТЗ и интерфейс | Границы версии, контракты изменений, обе темы, сценарии управляющих промптов |
| 2. Хранение | PostgreSQL, перенос тестовой копии данных и проверка восстановления |
| 3. Исполнение | Redis, независимый сбор/анализ, прогресс, лимиты, отмена и восстановление |
| 4. Диагностика и доставка | Скриншоты, отдельный vision-контекст, адаптер уведомлений; объём интеграции с мессенджером выбран |
| 5. Развёртывание | Рабочий облачный/гибридный вариант, доступ пользователя и ручная проверка HH |
| 6. Стабилизация | Сквозная проверка сценариев, документация запуска и итоговый выпуск |

Для устанавливаемых промежуточных сборок использовать обозначения
`0.2.0-alpha.1`, `0.2.0-alpha.2` и далее; после готовности функций —
`0.2.0-beta.1`, при необходимости `0.2.0-rc.1`, затем стабильный `0.2.0`.
Номер alpha не обязан совпадать с номером этапа. Выпуски помечать Git-тегами;
рабочая ветка остаётся `jobradar-v0.2`. Теги ставятся на проверенные конкретные
коммиты, а не заранее. Текущий номер пакета пока не меняется: код v0.2 ещё не написан.

После выпуска `0.2.0` исправления обычно обозначаются `0.2.1`, `0.2.2`.
Следующий согласованный набор возможностей можно выпустить как `0.3.0`.
Не нужно откладывать полезный проверенный выпуск до завершения всего облачного
перехода: при росте объёма явно перенести оставшиеся направления в следующий
выпуск и обновить границы концепции. Для версий до 1.0 правила совместимости
и миграций описывать в заметках к каждому выпуску.
