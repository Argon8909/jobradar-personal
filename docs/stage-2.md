# JobRadar v0.1 — Profile/Context Manager

Второй этап выполнен поверх схемы первого. Логическая модель, системные промпты
и опубликованные входные контракты не менялись. Перед реализацией перепроверены
страницы Confluence: 1605719 v4, 2359317 v8, 2490371 v1 — версии прежние.

## Реализовано

- `ProfileManager`: list_profiles, create_profile, switch_context,
  return_to_general, list_contexts, create_context, update_profile, update_context.
  Это методы предметного сервиса; регистрация обработчиков Tool Calling будет позже.
- `start_session` и `get_state` — внутренние операции приложения, не LLM-инструменты.
  Сервер задаёт user_id/session_id; пользователь LLM не может выбирать владельца.
- Создание профиля, первого контекста «Основной поиск» и его активация — одна
  транзакция. Дополнительный контекст создаётся и активируется также атомарно.
- Каждый вызов проверяет владельца сессии и активного/целевого контекста.
  Режим считывается заново из БД. Создание профиля доступно только из общего режима;
  изменение данных и создание контекста — только из активного.
- Частичные обновления сохраняют остальные поля; массивы заменяются целиком;
  salary объединяется по переданным вложенным ключам, null очищает допустимое поле.
- revision/criteria_revision повышаются только при реальном изменении.
  Старые персональные оценки сохраняются с прежними версиями, поэтому могут быть
  распознаны как устаревшие. Пересчёт оценок относится к будущему Search Manager.
- Внутренний expected_revision позволяет отклонить устаревшую запись.
  Он не добавлен в утверждённые аргументы инструментов.
- SQL отделён в `storage/profiles.py`; сервис независим от Flask/DeepSeek.

## Валидация и подтверждение

`tools/definitions.json` содержит точные 11 определений из утверждённой страницы
2490371 v1. Добавлена зависимость jsonschema для проверки этих схем, включая
вложенные объекты и запрет лишних полей. Не создаётся альтернативный ручной валидатор.
NaN/Infinity и не-JSON объекты отклоняются до записи.

Изменяющие методы по умолчанию возвращают ошибку CONFIRMATION_REQUIRED через
ProfileError. Только доверенный слой приложения после установления явного намерения
или согласия передаёт authorized=True. Это внутренний флаг, не поле JSON Schema
и не аргумент, который разрешено принимать от LLM. Распознавание реплик «да»,
связывание согласия с действием/контекстом, протухание согласия при смене темы
и уведомления пользователю будут подключены вместе с Dialogue Agent.

Смысловое выявление похожих профилей также остаётся ответственностью Dialogue Agent:
сервис не вводит самовольную уникальность профессии и не сливает данные.
Удаление профилей/контекстов не реализовано, поэтому операции удаления последнего
контекста через этот сервис нет.

## Проверки

`python -m unittest discover -s tests/v01 -v`: 41 тест, включая 20 новых тестов
профилей/контекстов. Проверяются откаты на ошибке активации, изоляция пользователей
и сессий, невалидные аргументы, вложенные обновления, конфликт редакций, отсутствие
потери параллельных изменений, сохранение истории и работа после повторного открытия.

`python -m unittest discover -s tests -v`: 9 регрессионных тестов старой версии.
Проверки выполнены на Linux/Python 3.12, без реальных HH/DeepSeek-запросов.
