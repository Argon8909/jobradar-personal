# JobRadar v0.2 — локальная приёмка на Windows

Это ручная проверка реальных HH.ru, DeepSeek и вашей копии накопленных данных.
Облачные автоматические тесты её не заменяют. Итог приёмки принимает пользователь.
Команды ниже рассчитаны на **PowerShell**, открытый в папке проекта, где лежат
`README.md`, `pyproject.toml`, `config` и `.venv`. Блоки выполняйте по порядку в одном
окне. Python активировать не требуется: указан полный путь к нему внутри `.venv`.

## 1. Остановить старую версию и обновить проект

В терминале со старым приложением нажмите **Ctrl+C**, дождитесь приглашения ввода.
Завершите незаконченный hh-login и закройте открытое им окно Chromium. Не запускайте
две копии JobRadar на одном порту или браузерном профиле.

```powershell
git status --short --branch
git switch jobradar-v0.2
git pull --ff-only
git log -3 --oneline
.\.venv\Scripts\python.exe --version
.\.venv\Scripts\python.exe -m pip install -e .
.\.venv\Scripts\python.exe -m pip check
.\.venv\Scripts\python.exe -m playwright install chromium
```

Если Git сообщает о локальных изменениях или не даёт переключить ветку, сохраните
сообщение и разберитесь с изменениями. Не используйте reset --hard и не удаляйте
свои конфигурации/.env/SQLite ради обновления. В истории должен быть коммит этапа 4,
ссылка на который дана в сообщении поставки, после базового `1e2317c`.

Если `.venv` отсутствует, сначала выполните `py -m venv .venv`.
Ожидается Python 3.11+; в облаке проверено на 3.12, Windows пока не проверена.

## 2. Создать отдельный контур приёмки с копией базы

Основной вариант запуска v0.2:

```powershell
.\.venv\Scripts\python.exe -m jobradar serve --config config/v0.2.json
```

Для испытаний ниже используем **копию SQLite и отдельный браузерный профиль**.
Так изменения критериев и новые вакансии не затрагивают рабочую базу. Исходные
профили, авторизация HH и `config/v0.1.json` не меняются.

Следующий блок читает путь вашей базы из `config/v0.2.json`, делает согласованную
копию SQLite через backup API и создаёт локальные настройки в игнорируемой папке
`data`. Если в v0.2 указан не тот путь к накопленной базе, сначала исправьте это
в своей локальной конфигурации: не подменяйте базу пустым файлом.

```powershell
$jrStamp = Get-Date -Format "yyyyMMdd-HHmmss"
$jrRun = Join-Path (Get-Location).Path ("data\acceptance-" + $jrStamp)
$jrConfig = Join-Path (Get-Location).Path ("data\acceptance-config-" + $jrStamp + ".json")
$env:JOBRADAR_ACCEPTANCE_RUN = $jrRun
$env:JOBRADAR_ACCEPTANCE_CONFIG = $jrConfig
@'
import json, os, sqlite3
from pathlib import Path
from jobradar.config import load_settings
s = load_settings("config/v0.2.json")
run = Path(os.environ["JOBRADAR_ACCEPTANCE_RUN"])
config = Path(os.environ["JOBRADAR_ACCEPTANCE_CONFIG"])
if not s.database_path.is_file():
    raise SystemExit("Накопленная база не найдена: " + str(s.database_path))
run.mkdir(parents=True, exist_ok=False)
with sqlite3.connect(s.database_path.as_uri() + "?mode=ro", uri=True) as source:
    with sqlite3.connect(run / "acceptance.sqlite3") as target:
        source.backup(target)
v = json.loads(s.config_path.read_text(encoding="utf-8-sig"))
v["database"]["path"] = str(run / "acceptance.sqlite3")
v["prompts_dir"] = str(s.prompts_dir)
v.pop("search", None)
v["search_config"] = str(run / "search.json")
(run / "search.json").write_text(json.dumps(s.values["search"], indent=2), encoding="utf-8")
config.write_text(json.dumps(v, ensure_ascii=False, indent=2), encoding="utf-8")
print("Рабочая база не изменена:", s.database_path)
print("База приёмки:", run / "acceptance.sqlite3")
print("Конфигурация приёмки:", config)
'@ | .\.venv\Scripts\python.exe -
```

При ошибке не продолжайте: скопируйте её текст. Сохраните выведенные пути.
Конфигурация остаётся непосредственно в `data`, поэтому приложение продолжает
читать ключ из прежнего `.env` в корне проекта. Секреты не копируются в JSON.

## 3. Проверить Chromium и авторизацию HH

Обычный авторизованный Chrome/Edge и браузер JobRadar — разные профили. Копия
приёмки использует `$jrRun\browser-hh`; первоначально он пустой. Авторизуйте его
обычной существующей командой:

```powershell
.\.venv\Scripts\python.exe -m jobradar hh-login --config $jrConfig
```

Должен открыться видимый Chromium на HH.ru. Войдите вручную, убедитесь, что видите
свой аккаунт. Если появилась CAPTCHA, решите её сами. Затем вернитесь в терминал
и нажмите Enter, как просит программа. Это закроет окно и сохранит профиль приёмки.
Команда не вызывает DeepSeek. Если браузер не открывается, сохраните ошибку;
проверьте установку Chromium предыдущей командой и отсутствие другого hh-login.
Не удаляйте рабочий `data\browser-hh` и не присылайте его cookies/содержимое.

## 4. Настроить небольшой первый прогон и запустить сервер

Откройте **копию** поисковых настроек:

```powershell
notepad (Join-Path $jrRun "search.json")
```

Для первого прогона можно поставить 10 / 2 / 10 / 120 / 3 / 30:

```json
{
  "max_source_vacancies": 10,
  "max_new_analyses": 2,
  "deadline_seconds": 120,
  "max_llm_calls": 10,
  "target_count": 3,
  "vacancy_max_age_days": 30
}
```

Это 10 уникальных обнаружений HH, 2 попытки нового анализа, 10 специализированных
попыток модели, 120 секунд, цель 3 и возраст 30 дней. Переоценки и работа с тегами
также расходуют общий LLM-бюджет. Новые анализы имеют отдельный счётчик. Результатов
может быть меньше из-за фильтров/ошибок и больше цели: цель не останавливает сбор.
Локальные кандидаты не расходуют квоту HH. Обработка синхронная; лимиты не обещают,
что за 120 секунд обязательно будут прочитаны все 10 объявлений.

Изменение файла применяется при перезапуске. Не редактируйте ради приёмки
`config/v0.1.json` или общие рабочие лимиты. Для полного прогона позднее можно
вернуть в копии значения 100 / 30 / 100 / 600 / 20 / 30.

Запуск с сохранением консольного журнала:

```powershell
$env:PYTHONUTF8 = "1"
$OutputEncoding = [Console]::OutputEncoding = [System.Text.UTF8Encoding]::new()
.\.venv\Scripts\python.exe -u -m jobradar serve --config $jrConfig 2>&1 | Tee-Object -FilePath (Join-Path $jrRun "console.log")
```

Терминал остаётся занят сервером. Откройте `http://127.0.0.1:8765`.
Если адрес/порт изменены в конфигурации, используйте их. При «порт занят» найдите
терминал старого JobRadar и остановите его Ctrl+C, не завершайте случайные процессы.

Откройте в браузере отдельное окно InPrivate/Инкогнито и используйте его для
приёмки: так cookie новой копии не заменит вашу обычную сессию. Во время проверки
не открывайте прежний сервер в том же окне. При копировании базы прежние профили
должны присутствовать, но активный контекст в новой браузерной сессии нужно выбрать.

## 5. Проверить DeepSeek и выбрать контекст

Следующие сообщения уже обращаются к **платному DeepSeek**. Выполняйте их, только
если готовы расходовать токены своего ключа. Даже вопрос без поиска обычно
требует нескольких диалоговых запросов. Наличие строки ключа само по себе не
подтверждает доступ к модели и баланс.

1. «Покажи мои профили». Ожидаются реальные профили из копии базы; список не должен
   выдумываться. В журнале появляются generation_completed и usage, если провайдер
   прислал статистику. Это подтверждает реальный ответ модели; успешное создание
   контекста в шаге 3 дополнительно проверяет Tool Calling.
2. «Переключись на контекст [точное название из списка]». Проверьте название слева.
3. «Создай отдельный контекст “Приёмка v0.2” с направлениями системный анализ и
   интеграции API, форматом удалённо и географией Россия». Используйте свои реальные
   направления. Он создаётся только в копии базы; профессиональный профиль прежний.

При ошибке ключа/баланса/модели сохраните сообщение. Проверьте `.env` в корне и
название модели в конфигурации. Ключ не вставляйте в чат и не прикладывайте к отчёту.
Не повторяйте платный поиск многократно, пока причина подключения не ясна.

## 6. Сценарии чата

Для каждого сценария запишите сообщение, номер поиска, ожидаемый и фактический
результат. Диагностика: `http://127.0.0.1:8765/diagnostics` в той же сессии браузера;
выберите соответствующий номер. Кнопка **«Скачать диагностический JSON»** сохраняет
его в загрузки. При изменении контекста список задач относится к новому контексту.

| Шаг / сообщение | Ожидаемое поведение |
|---|---|
| «Покажи сохранённые условия моего поиска» | Условия действующего контекста, без создания профиля и запуска поиска. Сохраните ответ для сравнения. |
| «Найди вакансии по моему профилю» | Карточки из SQLite обрабатываются первыми; далее исходники, затем HH. Готовые результаты появляются до окончания. Вакансия не дублируется в подборке; технический журнал не вываливается в чат. |
| «Почему ты нашёл так мало вакансий?» | Объяснение реального плана, отсева и ограничений последнего поиска. Нового номера поиска и изменений критериев нет. «Не знаю» допустимо при отсутствии подробной диагностики. |
| «Найди также работу с интеграциями и AI-автоматизацией» | Текущий профиль/контекст сохранён, нет обязательного создания нового. В плане — обоснованные варианты на основе фактических навыков; желание перейти в AI не превращается в выдуманный опыт. |
| «Ищи только системных аналитиков, смежные роли не нужны» | План не расширяет явно ограниченное направление. Если качество плана или локальной выдачи спорное, приложите примеры; моки этого не доказывают. |
| «Ищи вакансии не старше недели» | Период weeks:1, источник request; проверка до платного анализа. Критерии и criteria_revision не меняются. |
| «Повтори поиск по сохранённым условиям» | Разовая неделя не переносится. Период снова берётся из контекста либо глобальной настройки. |
| «Покажи за последние два месяца» | Источник request, months:2, календарная граница, не произвольные 60 дней. Ранее сохранённые подходящие записи могут вернуться. |
| «Ищи без ограничения по дате» | Источник request, unlimited, cutoff отсутствует. Подтверждённо закрытые записи всё равно не предлагаются как доступные. |
| «В дальнейшем рассматривай вакансии только за последние 14 дней» | update_context, период days:14 сохраняется, ревизия растёт только при реальном изменении. Остальные условия и профиль не теряются. Поиск сам по себе не обязателен. |
| «Найди вакансии по сохранённым условиям» | Период 14 дней, источник context. |
| «Найди разово вакансии не старше недели» → следующий поиск по сохранённым условиям | Сначала request/неделя, потом context/14 дней. |
| «Ищи со стандартным периодом поиска» | Только для этого запуска глобальные 30 дней, источник request и reset_to_default=true. Сохранённые 14 дней остаются. |
| «В дальнейшем верни стандартный период поиска» → новый поиск | Сохранённый default наследует глобальную настройку. Профиль, зарплата, формат и география не меняются. |
| При конкретном предложении ассистента: «да» | Выполняются ровно показанные аргументы. Уточнение вопросом вместо согласия не должно выполнять предложение; случайное позднее «да» не должно воскрешать старое действие. |

Не ждите одинакового количества вакансий между живыми поисками: сайт, даты,
тексты, лимиты и доступность меняются. Проверяйте правила и конкретные ID.
Два месяца и ровную границу месяца надёжно проверяют автоматические фикстуры;
подходящих реальных публикаций на нужной границе может не быть.

**География:** проверьте сохранение названного региона и отсутствие произвольных
числовых HH-ID. Для «ближнего зарубежья» допустимо уточнение стран. Самостоятельное
разовое переопределение уже сохранённой географии пока имеет известное ограничение
(см. отчёт этапа 4); не считайте такую реплику доказанно поддержанной.

## 7. Проверить кэш карточек и сохранность критериев

Поиск всегда может платить за Planner; «карточки переиспользованы» не означает
«расход токенов нулевой». При неизменном профиле/критериях и том же исходнике:

- Рост cache_hits — повторное использование оценки.
- assessment_only — допустимая новая оценка без извлечения при изменённой ревизии.
- extract_and_assess для того же ID допустим, если текст/содержательные поля или
  версия извлечения действительно изменились. Одного появления/изменения даты
  публикации для повторного извлечения недостаточно.

В панели раскройте «Вызовы LLM», смотрите vacancy_id, prompt и, при сохранённом
теле, mode. По умолчанию успешные тела не сохраняются (capture_llm=errors).
Для подробной проверки временно задайте в **локальном конфигурационном JSON
приёмки** diagnostics.capture_llm="all" и перезапустите сервер. Тогда журналы
содержат персональные сведения; после проверки верните errors.

Для точного сравнения карточек можно сделать два CSV-снимка, не меняющих базу.
Остановите сервер Ctrl+C и в том же PowerShell определите функцию:

```powershell
function Save-JobRadarCards([string]$Destination) {
@'
import csv, sqlite3, sys
from jobradar.config import load_settings
s = load_settings(sys.argv[1])
with sqlite3.connect(s.database_path.as_uri() + "?mode=ro", uri=True) as db:
    rows = db.execute("SELECT c.vacancy_id,v.external_id,c.source_hash,c.extraction_version,c.extracted_at FROM vacancy_cards c JOIN vacancies v ON v.id=c.vacancy_id ORDER BY c.vacancy_id")
    with open(sys.argv[2], "w", encoding="utf-8-sig", newline="") as f:
        w = csv.writer(f)
        w.writerow(["vacancy_id","external_id","source_hash","extraction_version","extracted_at"])
        w.writerows(rows)
'@ | .\.venv\Scripts\python.exe - $jrConfig $Destination
}
Save-JobRadarCards (Join-Path $jrRun "cards-before.csv")
```

Запустите сервер, выполните один поиск, не меняя профиль/критерии, остановите
сервер и выполните:

```powershell
Save-JobRadarCards (Join-Path $jrRun "cards-after.csv")
Compare-Object (Import-Csv (Join-Path $jrRun "cards-before.csv")) (Import-Csv (Join-Path $jrRun "cards-after.csv")) -Property vacancy_id,source_hash,extraction_version,extracted_at
```

У уже актуальных неизменившихся карточек все перечисленные поля должны совпасть.
Новые ID и действительно изменённые исходники объясняют допустимые различия.
Снимок до первого полного поиска может включать устаревшие карточки: их первое
обновление нормально. Для проверки повторного использования сравнивайте два
последующих запуска. Для разового периода дополнительно проверьте, что сохранённые
criteria_revision/criteria и profile.revision не изменились (раздел 10 ниже).

## 8. Проверить лимиты и токены

В JSON одного завершённого поиска проверьте:

| Поле | Что проверять |
|---|---|
| diagnostics.metrics.hh_discovered | Не больше max_source_vacancies; это обнаружения, а не число созданных карточек. |
| hh_read / hh_saved / hh_incomplete / hh_duplicates | Чтения, сохранения и повторы различаются. Повтор ID в задаче не расходует квоту заново. |
| analysis_attempts | Не больше max_new_analyses. Ошибки тоже расходуют попытку. |
| specialized_llm_calls | Попытки специализированных вызовов основного поиска, включая сетевые повторы. Не больше max_llm_calls. Не включает диалоговые вызовы. |
| diagnostics.llm_calls | Записи структурированных вызовов/исправлений. Одна запись может иметь transport_attempts > 1; число строк не равно числу HTTP-попыток. |
| usage.prompt_tokens / completion_tokens / total_tokens в записи вызова | Статистика успешного ответа, если провайдер её прислал; не денежный лимит. |
| coverage, stop_reason, diagnostics.stop_reason | Реальное завершение этапов, неполный охват, лимит или ошибка. Пустой успешный поиск может иметь stop_reason=null в БД и причину недостижения цели в diagnostics.stop_reason. |

Впоследствии просмотр результатов может вызвать отдельную переоценку со своим
бюджетом и добавить записи в журнал задачи. specialized_llm_calls фиксирует
основной запуск; не сравнивайте с ним без пояснения сумму всех последующих
просмотров. Дополнительные вызовы диалогового агента имеют отдельный лимит на реплику.

Для проверки общего расхода сохраните время начала/окончания прогона и сравните
usage/баланс в кабинете DeepSeek до и после. Не используйте тот же ключ параллельно
в других программах, если хотите сопоставить расход. Консольный журнал содержит
успешные генерации и для диалога, и для поиска. После остановки сервера:

```powershell
$jrCalls = Get-Content (Join-Path $jrRun "console.log") | ForEach-Object {
  if ($_.TrimStart().StartsWith("{")) {
    try { $_ | ConvertFrom-Json -ErrorAction Stop } catch { }
  }
} | Where-Object { $_.component -eq "llm" -and $_.event -eq "generation_completed" }
$jrCalls | Select-Object time,attempt,prompt_tokens,completion_tokens,total_tokens
$jrCalls | Measure-Object -Property total_tokens -Sum
```

Это сумма известных успешных ответов **только данного файла**; она не гарантирует
равенства счёту провайдера. При сетевой ошибке запрос мог быть обработан, а usage
не получен. Повторный запуск с тем же console.log перезаписывает файл: перед новым
запуском скопируйте его под другим именем. Нулевые/неполные usage не доказывают
отсутствия списаний. Последнее слово о платеже — кабинет DeepSeek.

Для проверки времени можно временно уменьшить deadline_seconds в копии настроек
и перезапустить. Ожидается частичный итог и сохранение уже полученных исходников,
а не обязательное точное время ответа по секундомеру. Не провоцируйте CAPTCHA
массовыми запросами. Если она появилась естественно, завершите её вручную в окне
HH в отведённое время; при истечении ожидания уже сохранённые записи остаются.

## 9. Ошибки, журналы и передача результатов

При неожиданном поведении:

1. Не повторяйте действие вслепую. Запишите сообщение пользователя, время, номер
   поиска, URL/ID вакансий и наблюдавшийся результат.
2. В `/diagnostics` выберите этот поиск, скачайте JSON. При необходимости раскройте
   ответ LLM, схему/ошибку валидации, план и события. В обычном чате их быть не должно.
3. Сохраните console.log, результат `git log -1 --oneline`, версии Python и
   `pip check`, а также значения поисковых лимитов из копии search.json.
4. Укажите, была ли CAPTCHA/авторизация и что показывал отдельный Chromium.
5. Передайте выбранные файлы и описание ожидаемого поведения в чат для анализа.

Файлы текущих диагностик находятся в `$jrRun\search-diagnostics\task-N.json`.
По умолчанию тела ошибок сохраняются, успешные — только при capture_llm=all;
действуют срок хранения 7 дней и лимиты размера. Отсутствие тела может означать
настройку/очистку/ограничение размера, а не отсутствие вызова.

Не присылайте `.env`, API-ключ, браузерный профиль или cookies. Диагностический
JSON может содержать данные резюме/критериев и тексты вакансий: перед отправкой
проверьте его. Весь каталог приёмки архивировать для передачи не нужно.

## 10. Дополнительная проверка критериев без доверия к тексту модели

`/api/state` показывает выбранные профиль/контекст, но не полный набор критериев.
Ответ «покажи условия» может ошибиться. Чтобы точно сверить состояние копии SQLite,
остановите сервер и выполните блок до/после спорного сценария, меняя имя файла:

```powershell
@'
import json, sqlite3, sys
from jobradar.config import load_settings
s = load_settings(sys.argv[1])
with sqlite3.connect(s.database_path.as_uri() + "?mode=ro", uri=True) as db:
    contexts = db.execute("SELECT id,title,profile_id,criteria_revision,criteria FROM search_contexts ORDER BY id").fetchall()
    profiles = db.execute("SELECT id,revision,profile_data FROM user_profiles ORDER BY id").fetchall()
print(json.dumps({"contexts":contexts,"profiles":profiles}, ensure_ascii=False, indent=2))
'@ | .\.venv\Scripts\python.exe - $jrConfig | Set-Content -Encoding UTF8 (Join-Path $jrRun "criteria-before.json")
```

Для разового поиска значения должны остаться прежними. Постоянное изменение
периода обновляет только критерии текущего контекста; остальные условия и все
профили прежние. Файл содержит личные данные, храните его у себя.

## 11. Завершить испытания

Остановите сервер Ctrl+C, сохраните выбранные диагностики. Основная SQLite и её
авторизация HH остались нетронутыми; тестовые изменения находятся в отдельной
копии. Запуск обычной версии — с `--config config/v0.2.json` в обычном окне браузера.
Не переносите тестовую базу поверх рабочей без отдельного осознанного решения.

Сообщите результат по каждому сценарию: **пройден / ошибка / не проверен** и
приложите данные для ошибок. Неизвестные даты, отсутствие свежих подходящих записей
или недоступность интеграции отмечаются явно. До этой проверки JobRadar v0.2
считается подготовленным к локальной приёмке, а не окончательно принятым.
